1 · The puzzle

Two neighbours: one digit and seventeen

Type 0.3 and JavaScript prints 0.3. Type 0.1 + 0.2 and it prints 0.30000000000000004. The two results are adjacent doubles: their bit patterns differ by exactly one.

xjb runs exactly the same twelve lines for both numbers, without branching. The registers hold different values, of course, but the decisive difference is a single unsigned comparison that comes out true for one number and false for the other. By the end of the stepper below you will know which one and why.

Remember

A positive double is exactly v = c · 2q, with an integer significand c (53 bits for normal numbers) and a binary exponent q. Its neighbours are 2q away. The one exception is the neighbour below an exact power of two, which is only half as far away.

Every decimal closer to v than halfway to either neighbour reads back as v. That is the rounding interval. Its ends count too when c is even, because a tie between two doubles rounds to the even significand.

Shortest printing picks the decimal in that interval with the fewest digits. If several have that length, it takes the one closest to v.

2 · The plan

Put the decimal point one digit early

Let k = ⌊q · log10 2⌋. Then 10k ≤ 2q < 10k+1, so the gap between neighbouring doubles is between 1 and 10 units of 10k. No useful output digit is finer than the 10k place. xjb scales by one decade more than that, and splits the result:

v · 10−k−1 = m + n

Here m is an integer and 0 ≤ n < 1. m holds every digit except the last one (15 or 16 digits for a normal double). n is the position inside the cell from m to m+1, whose tenths are the candidate last digits. The half-gap in the same units is H = 2q−1 · 10−k−1. It depends only on q, and always lies in [0.05, 0.5): at least half a tick, and less than half the cell. That leaves exactly three outcomes:

  1. down: the interval reaches m, so drop the last digit;
  2. up: the interval reaches m + 1, so carry and drop the last digit;
  3. otherwise print m followed by the nearest tick, round(10n). It is always inside, because the interval covers at least one tick.

This is Schubfach’s decision, re-parametrised, and xjb’s README states that its outputs are identical to Schubfach’s. What xjb changes is how cheaply the machine obtains m, n and H. That is what the code does. (Approach A builds this ruler picture first; here it appears as a side effect of the registers.)

3 · The code

Step through xjb64

Pick a number and press Step. The ←/→ keys also work while the figure has focus. The presets cover every branch: nearest digit, carry up, drop down, both kinds of tie, a subnormal, and two powers of two, which leave for their own branch at the end.

Three things to notice

The table word is used twice. Multiplied by c it gives m and n. Shifted right by one to four bits it is the half-gap H, because H = 2q−1 · 10−k−1 does not involve c at all. The shifted word equals ⌊H · 264⌋ exactly, for every exponent (this page’s tests check all 2047 exponent fields).

“≥” costs one addition. When c is even the interval ends belong to it. Adding 1 to half_ulp turns every strict test half_ulp > x into H ≥ x. The paper proves these integer comparisons are exact, including the equality cases.

The last digit never needs a division. m is the integer part of the product and one is the high word of 10 · dot_one. d = 10 · m_up + one is never even formed: m_up goes straight to digit printing and one is appended.

4 · The unlikely branch

Powers of two get their own branch

When the stored fraction is zero, v is a power of two and the double below it is only half a gap away. The interval is lopsided: L = H/2 below v, H above. The twelve lines assume a symmetric interval, so the source finishes with an [[unlikely]] branch that recomputes k, m_up, one and up_down:

// sig == 0, exponent field 1…2046: c = 2^52, so c · pow10 is just a shift
k        = (q * 315653 - 131072) >> 20;       // ⌊q·log10 2 − log10(4/3)⌋
h        = q + ((k * -217707 - 217707) >> 16);
pow10_hi = table[-k - 1].hi;                  // only the high word
half_ulp = pow10_hi >> -h;                    // H: upper half-gap
dot_one  = pow10_hi << (53 + h);              // n
up       = half_ulp > ~dot_one;               // same carry test
down     = (half_ulp >> 1) > dot_one;         // L = H/2 below
m_up     = (pow10_hi >> (11 - h)) + up;
one      = ((dot_one >> (53 + h)) * 5 + (1 << (9 - h))) >> (10 - h); // round(10n)
if ((((dot_one >> 54) * 5) & 511) > ((half_ulp >> 55) * 5))           // frac(10n) > 10·L ?
    one = (((dot_one >> 54) * 5) >> 9) + 1;   // fell off the short side: next tick up
if (dot_one == 1ull << 62) one = 2;           // tie at n = ¼

Three changes. First, k is picked for a ¾-gap-wide interval, so the interval still covers at least one tick. Second, the drop-down test uses L. Third, if the nearest tick lies below the short lower end, the tick above is used; it is inside, because the interval is at least one tick wide. The carry test is unchanged. The two comparisons use only 9–10 bits, and they are justified by testing all 2046 cases, not by proof.

The published paper’s Algorithm 1 puts the carry test inside the “regular” branch, so powers of two could never carry. The README flags “a mistake in Algorithm 1 on page 10” and gives a corrected version with the carry test outside. The source does what the correction says. The counts above show the correction matters: the carry fires for hundreds of powers of two. The smallest normal power, 2−1022, has a subnormal neighbour below at the full gap, so its interval is not actually lopsided. xjb treats it as irregular anyway, and still prints the right answer.

5 · Why this shape is fast

Two independent outputs, no division

Speed claims belong to benchmarks, and this page runs none. What it can show is the shape of the work. The graphs below compare Schubfach’s reference structure (the port bundled in xjb’s benchmark folder) with the xjb path above. Arrows mean “needs the result of”.

Scaling once, reading the interval off the same power, and splitting off the last digit are not unique to xjb. The README says it was inspired by yy (yy_double) and that parts of it are derived from Żmij, and those algorithms share related tricks. The fair comparison here is with Schubfach, whose mathematics xjb reuses and whose output it matches.

6 · Evidence

What is proved and what is tested

Proved (paper, computer-assisted per exponent)

  • m is exact even though table entries are rounded up. At least 113 bits are needed, and the table has 128. The bound comes from Farey-sequence / best-rational-approximation enumeration per exponent (py_test/test1.py).
  • The half_ulp vs dot_one comparisons decide membership exactly, including the case where n equals the bound.
  • Ties happen only at n = ¼ or ¾, and dot_one == 2^62 detects n = ¼.
  • The + 2^63 + 6 rounding of one is proved correct for every double except ten listed in the paper’s equations (171) and (173). Those ten were checked one by one (test8.py).

Tested (not proved)

  • The power-of-two branch: all 2046 cases compared against Schubfach. The paper leaves that branch out.
  • binary32: all 232 inputs, exhaustively. One step of the float proof is called “not-so-perfect” and leans on that test.
  • The whole binary64 pipeline: large random tests plus edge cases against Schubfach (bench/check.cpp, paper §4.1).

Caveats. The paper’s proofs are written for its pseudocode, which uses a 6-bit alignment (BIT = 6). The current source uses offset = 9, with the comment “offset in range [3,10] has same result”; that change is covered by testing, not re-proved. The README warns that Algorithm 1 in the paper contains a mistake: the carry test is missing for powers of two (see above). Sources: the paper, J. Xiang & T. Wang, “xjb: Fast Float to String Algorithm”, Computers 15(5):280, 2026, doi:10.3390/computers15050280; the repository, github.com/xjb714/xjb (commit 80cc895).

This page’s own check: the BigInt port behind the stepper reproduces the source’s table generator word for word. It prints the same digits as Number.prototype.toString on tens of thousands of random bit patterns, short decimals and subnormals, and on all 2046 powers of two. That is evidence for the port, not a proof of xjb.
