Tejú Jaguá: break the multiplier

Tejú Jaguá's runtime trusts one multiplication completely and never checks it. On this page you break that multiplication on purpose, find its worst input without trying them all, and then run the generator that proves all 617 binary64 constants.

Generator first. Make the one inequality visible on a toy row, let the reader break it with a shift slider, then run a BigInt port of the C++ generator. It proves every row and emits a C table that matches the repository byte for byte.

The deal

Floors you can trust

Remember

A positive double is x = m · 2e, with an integer significand m (53 bits) and a binary exponent e.

Its rounding interval reaches halfway to each neighbour: from (2m − 1) · 2e−1 to (2m + 1) · 2e−1. Any decimal inside reads back as x. When m is a power of two, the neighbour below is closer, so the lower end is (4m − 1) · 2e−2.

Tejú Jaguá measures the interval in units of 10F, with F = ⌊e · log10 2⌋. That makes the interval between 1 and 10 units wide.

To pick the output, the runtime needs the interval's ends in those units, rounded down. For the upper end that is b = ⌊(2m + 1) · 2e−1 / 10F⌋.

Several binary exponents share one F. Call the smallest of them e0 and write e = e0 + r, with r between 0 and 3. Then (2m + 1) · 2e−1 = ((2m + 1) ≪ r) · 2e0−1, so every floor the runtime needs looks like this:

⌊ n · α / δ ⌋   where   α / δ = 2e0−1 / 10F in lowest terms.

Here n is a small integer built from the significand, such as (2m + 1) ≪ r. The fraction α/δ is fixed for each F, and it is always a power of 2 over a power of 5 or the other way round. Tejú Jaguá stores one 128-bit number per F:

M = ⌊α · 2128 / δ⌋ + 1,   and computes   ⌊n · M / 2128⌋.

That second floor is simply the top 64-bit word of the 192-bit product n · M, so there is no division and no shift. Try it:

If this floor is always exact, the rest of the kernel is plain integer logic: compare a and b, look at one multiple of ten, check the parity of one more floor. Approach A walks through that kernel. This page is about the “if”. Nothing checks it at runtime. A separate program, the generator, proves it for every possible n before it writes the table into C.

Why it can fail

One inequality

M was rounded up, so n · M / 2k is slightly too big. (Here k is the shift: 128 for binary64. Keep it general, because we are about to shrink it.) How much too big is easy to write down:

n · M / 2k = n · α / δ + n · ε / (δ · 2k),
with ε = M · δ − α · 2k,   1 ≤ ε ≤ δ.

The extra term is the overshoot. It is tiny, but it grows with n. The floor stays correct as long as the overshoot does not push n · α / δ past the next integer. The distance up to that integer is the headroom:

headroom(n) = (δ − (α · n mod δ)) / δ.

The floor is right exactly when the overshoot is smaller than the headroom. Multiply both sides by δ · 2k / ε, and the condition splits into one side that depends only on n and one that depends only on the shift:

φ(n) = n / (δ − α · n mod δ)   <   2k / ε.

Each extra bit of k roughly doubles the right side. So the proof comes down to one number: the largest φ(n) over every n the runtime can produce. If it is below 2k/ε, every floor is exact.

Here it is on a toy row, α/δ = 8192/15625 = 213/56. This is row F = 6 of a made-up format with 5-bit significands, so n runs from 33 to 992. Each dot is the fractional part of n · α / δ. The descending line is 1 minus the overshoot. A dot above the line gets pushed past the next integer, so its floor comes out one too big.

On a linear scale the interesting part is invisible: the dots that fail sit a hair below the next integer, and at realistic shifts the line hugs the top edge. Two changes fix that. Plot the headroom (1 minus the fraction) instead of the fraction, and use logarithmic axes on both sides. Then the overshoot n · ε / (δ · 2k) becomes a straight line of slope one, and each extra bit of k moves it down by one grid step.

A lab

Break it

Both axes are logarithmic. Each dot is one n the generator must check: its headroom is its height. The ink line is the overshoot for shift k. Any dot on or below the line gets a wrong floor. Drag k down until dots turn red, then click one (or pick it from the list) to see the wrong floor.

The second row is real. binary16 row F = −8 has α/δ = 58/219 and 65 507 dots, and the page also runs every binary16 conversion with the shortened multipliers.

What the binary16 row teaches

At k = 23, n = 10320 is one of the red dots, and the runtime really uses it. It is mc = (4 · 645) ≪ 2, the operand of the final rounding step for x = 645 · 2−24. The exact value is 7688.99917…, so the headroom is 0.00082, but the overshoot is 10320 / 223 = 0.00123. The floor becomes 7689, which is odd, so the kernel rounds up, and x prints as 3.845e−5 instead of the correct 3.844e−5. The two candidates are 5.004·10−9 and 4.996·10−9 away from x: a near-tie flipped by one unit of error.

The proof is sufficient, not necessary. For all ten binary16 rows, the generator's check passes only from k = 33. But every binary16 conversion already prints correctly from k = 24. There are two reasons for the gap. The generator checks every n in a range, including the many grey n the kernel never produces. And a wrong floor does not always change the output: at k = 24, n = 16188 (a real mb) still gets a wrong floor, yet no printed digit changes. The generator does not try to be clever about this. It proves a clean, slightly conservative statement, and the real binary16 build uses 32-bit words, so k = 64: 31 bits to spare.

Search without searching

The worst n, without trying them all

For binary64 the generator must check n from 253 + 1 to 32 · (253 − 1). That is about 258 values per row, and there are 617 rows. Trying them all is out of the question. But the dots that matter are not scattered randomly. Here are the record holders of the toy row, each n with a larger φ than every n before it:

Record holders of phi for the toy row

After a short start, the records advance in arithmetic runs. Adding 21 to n always adds 21 · 8192 mod 15625 = 157 to α · n mod δ, so the gap to the next multiple of δ shrinks by 157: 445, 288, 131. Once the gap is smaller than 157, another +21 would jump past the integer. So a new step takes over: +103 shrinks the gap by 26, giving 105, 79, 53, 27, 1. At 597 the gap is 1, as small as it can be. Those step sizes are no accident: 21, 103 and 597 are denominators of the continued fraction convergents of 8192/15625 = .

The generator exploits the same structure with a recursion. Only an n that sits just below a multiple of δ can set a record. Index those n by the integer j that they sit just below. Measured in j, the gap becomes j · δ mod α: the same kind of problem, with (α, δ) replaced by (δ mod α, α). That is the Euclid step. The range of j is the range of n scaled by α/δ, so it shrinks at each level. The functions get_maximum_1 and get_maximum_2 alternate between two mirror-image forms (distance up to the next integer, distance above the previous one). At each level they keep the best endpoint and hand the rest down, until the range is a single value or empty.

This is a close cousin of continued fractions, not the textbook algorithm: the recursion carries a range [L, U] along and cuts it at every level. The page runs the generator's recursion and checks it against brute force wherever brute force is possible. It does not prove the recursion correct. The underlying theory of such multiply-and-shift divisions is in Neri and Schneider's paper on Euclidean affine functions.

The real thing

Generate binary64

For each decimal exponent F from −324 to 292, the generator does what you just saw:

  1. Find e0 and write 2e0−1/10F = α/δ.
  2. Set M = ⌊α · 2128/δ⌋ + 1 and ε = M · δ − α · 2128.
  3. Find the largest φ(n) over [253 + 1, 32 · (253 − 1)] with the recursion (from n = 1 for the lowest row), plus 16 extra operands of the power-of-two case.
  4. Require it to be below 2128/ε. Otherwise stop with “Unable to use shift that is twice the width.”

      Stage three
      
          
      A compiler for float formats
      
          
      The runtime is one generic C file, teju.h. Everything specific to a format comes from the generator. It reads a small JSON config (word width W, exponent range, significand width), runs the checks, and emits #defines and two tables. It never searches: if anything fails, it stops with an error. Pick a format, or break one:
      
          
          
      
            The repository's generated formats
            
      formatword Wshiftrowsminverse rowssortedtightest headroom
      
            
          
      
          
      Only binary16 comes out sorted. For every power of two, the lower end of its interval lands below the upper end on the 10F ruler, so the kernel's refined branch (one decade finer, operand 40m ≪ r) can never run, and the 8 + MW ≤ W check is skipped. For binary64, 33 powers of two need that branch. bfloat16 on 16-bit words passes with just 1.16 bits to spare.
