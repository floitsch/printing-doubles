Pocket Schubfach

Play the shortest-decimal game on 16-bit floats until you find a strategy that never needs more than four checks. That strategy is Schubfach. Then switch to 64-bit doubles and see how the fast version makes those four checks exact without big numbers.

Discover it yourself. In Act 1 the reader plays the algorithm by hand on half precision, where every number has 4–5 digits, and the page then shows that the best play is exactly Schubfach's. In Act 2, “the honest ruler”, the reader sees how multiplying by 4 and rounding to odd let one 126-bit table value and three multiplications give exact answers. Truncation and a naive sticky bit are shown failing live.

Before you play

The job

To print a floating-point number, pick the decimal with the fewest significant digits that reads back as the same number. If several are equally short, pick the one closest to the number. If two are equally close, pick the one whose last digit is even.

Remember: the rounding interval

Every float v has two neighbours. A decimal between v and the midpoint to either neighbour reads back as v. The set of such decimals is v's rounding interval.

A decimal exactly on a midpoint is a tie. Reading back rounds ties to the neighbour with an even significand, so the endpoints belong to v exactly when its significand c is even. Closed [ ] for even c, open ( ) for odd c.

At a power of two the neighbour below is only half as far away as the one above, so the interval is lopsided: it reaches ¼ gap down and ½ gap up.

Remember: half precision

binary16 is a real IEEE 754 format with 1 sign bit, 5 exponent bits and 10 fraction bits. GPUs and machine-learning code use it. A value is v = c·2q with an 11-bit significand (1024 ≤ c ≤ 2047 for normal numbers) and −24 ≤ q ≤ 5. That is about 3.3 decimal digits; the largest value is 65504.

Doubles work the same way with 53-bit significands. Half precision just keeps the numbers small enough to reason about in your head.

Act 1 · Pocket Schubfach

Find the shortest decimal

Each round converts a number to half precision and draws its rounding interval on a ruler. Choose a tick spacing and click ticks to check them. A check tells you whether that decimal reads back as the same half-precision number, and it costs one point. Then print one of the ticks you checked.

You see what the printer sees: the stored number v and how wide its interval is, but not exactly where the ends are. The interval appears once you print. A correct answer scores 10 minus the number of checks, and a wrong answer scores 0. The printer plays by the same rules and counts every check it makes.

The reveal

The strategy you found is Schubfach

Show the winning strategy (opens by itself when you finish round 7)

Look back at the “ticks inside” counts the debriefs showed you. Every round had the same pattern. One ruler had at most one tick inside the interval, and the next finer ruler had at least one. That is the pigeonhole principle, Schubfachprinzip in German, and it gives the algorithm its name.

  1. Choose the ruler from the width, not from the digits of v. Let k be the decade of the interval's width: 10k ≤ width < 10k+1. The width is 2q (or ¾·2q at a power of two), so k depends only on the exponent.
  2. Pigeonhole. The fine ruler with spacing 10k must have a tick inside, because the interval is at least one spacing wide. The coarse ruler with spacing 10k+1 can have at most one, because the interval is narrower than its spacing. Every coarser ruler's ticks are also ticks of the coarse ruler. So if anything shorter exists, it is that single coarse tick, and its trailing zeros show how short it really is.
  3. Check the two coarse ticks next to v: u′ just below and w′ just above. If one is inside, print it. That is the whole search for short answers.
  4. Otherwise, check the two fine ticks next to v: u = ⌊V⌋ and w = u + 1, where V is v measured in fine-ruler units. The fine ticks inside have no multiple of 10 between them, so they all have the same length. Only the two next to v can be the closest. At least one of them is inside. If both are, print the closer; on an exact tie, print the even one.
  5. Every check respects the endpoints: a tick exactly on an end counts only when c is even.

There is no digit loop and never more than four checks. The debriefs counted Schubfach's checks in exactly this order: u′, then w′, then u and w.

k = floor(log10(width))              // from q alone
V = v * 10^-k;  s = floor(V)         // v in fine-ruler units
if s >= 10:                          // coarse ruler, spacing 10^(k+1)
  if inside(10*floor(s/10))      -> print it   // u'
  if inside(10*floor(s/10) + 10) -> print it   // w'
u = s;  w = s + 1                    // fine ruler, spacing 10^k
if inside(u) and not inside(w)   -> print u
if inside(w) and not inside(u)   -> print w
print whichever of u, w is closer to V (tie: the even one)

Act 2 · The honest ruler

Now with 17 digits

Doubles use the same four checks. The fine ruler just has 16- or 17-digit ticks. For v = 0.3, for example, k = −17 and the interval spans 29999999999999996.11… to 30000000000000001.66… fine ticks.

The catch is the arithmetic. Computing Vℓ, V and Vr (the interval ends and v, times 10−k) exactly takes a big-number library. For some doubles that means hundreds of digits. But the algorithm never needs these values. It only needs yes/no answers to five questions, and each question compares one of them with an integer or a half-integer:

Vℓ ⪯ u′  ·  w′ ⪯ Vr  ·  Vℓ ⪯ u  ·  w ⪯ Vr  ·  V ⋚ (u+w)/2

Here ⪯ is ≤ for a closed interval and < for an open one. Multiply everything by 4 and every right-hand side becomes an even integer: 4u′, 4w′, 4u, 4w and 2(u+w). So for each of 4Vℓ, 4V and 4Vr we only need to know one of two things: that it lies exactly on some even integer (and which one), or that it lies strictly between two neighbouring even integers (and which two).

Keeping just enough

Round to odd

Giulietti's paper packs exactly that information into one integer with a rounding it calls round to odd:

ro(x) = x if x is an even integer, otherwise the odd integer between x's two even neighbours

In code this is ⌊x⌋ with its lowest bit set whenever x is not an integer: truncate, then keep a “something was cut off” bit. That is the same idea as the sticky bit in IEEE hardware, but applied to an integer estimate, not to a float's significand. An even result is an exact mark; an odd result says “strictly inside this half-cell”. Every comparison with an even integer 2h therefore comes out the same for ro(x) as for x. As a bonus, ⌊ro(4V)/4⌋ = ⌊V⌋ = s, so the fine anchor falls out of the same number.

Making it fast

One table value, three multiplications

Schubfach reads the three estimates off three products. v = c·2q, so the interval ends and v are c̄ℓ·2q−2, c̄·2q−2 and c̄r·2q−2, with integer c̄ = 4c, c̄r = 4c+2 and c̄ℓ = 4c−2 (4c−1 at a power of two). For the factor 10−k it uses a table of 617 entries, one per possible k:

g = ⌊10−k · 2−r⌋ + 1,   r = ⌊log₂ 10−k⌋ − 125,   so 2125 < g < 2126

g is a 126-bit overestimate of 10−k, scaled up by a power of two. With the shift h = q + ⌊log₂ 10−k⌋ + 2 (always 2 to 5), each estimate is one product, a 64-bit integer times the 126-bit g:

4V′ = (c̄ · 2h) · g / 2127

The product has at most 186 bits, in three bands. Bits 127 and up are ⌊4V′⌋. Bits 64–126 decide the sticky bit. Bits 0–63 are ignored: that is where the tiny excess of g ends up. This slightly modified rounding is the paper's ro′. Why ignoring those bits is safe comes last. First, see the three rounding choices on real doubles.

Truncate, naive sticky, or round to odd

When the ruler lies

Truncation turns 4Vℓ into exactly 4u′, so u′ seems to be on the closed end and is accepted. The printer outputs 1.443060662446e122, which is a different double.
  • 18014398509481988 (= 254 + 4, c odd, so the interval (…986, …990) is open): here k = 0 and g = 2125 + 1. The “+1” leaves dust in the low bits even though 4Vr is an exact even integer. A naive sticky bit over all the low bits calls it inexact, so the excluded end …990 passes the test. The printer outputs 18014398509481990, which reads back as 18014398509481992.
  • 1476640867921609.25: V is exactly halfway between two fine ticks. A naive sticky bit breaks this tie the wrong way and prints …609.3 where round to odd prints …609.2.

Measure it

Fuzz it

How often does each shortcut go wrong? The fuzzer below draws random bit patterns (positive, finite) and prints each double three ways. It compares every result with your browser's own String(v), which is also shortest-then-closest. Nothing is precomputed: the counts come from this run.

Truncation fails often. The naive sticky bit fails rarely: it only goes wrong when an interval end, or v itself, lands exactly on a comparison target (an endpoint on a tick, or an exact tie). Rare failures are the dangerous kind, because testing easily misses them. Round to odd with the 64-bit cutoff never fails, and not only on this sample, as the next section explains.

The proof obligation

Why 126 bits suffice

ro′ ignores bits 0–63. That is only safe if two things hold for every double.

  1. The error is tiny. g exceeds the exact scaled power by less than one unit, so V′ − V < 2−68. The same holds for Vℓ and Vr. When 2V is an exact integer, all of the excess lands below bit 64 (in the product's units), and ro′ correctly reports “exact”.
  2. Inexact values are never that close. If 2V is not an integer, its distance to the nearest integer must be larger than the region ro′ ignores. Otherwise a genuinely inexact value could be mistaken for an exact one.

The second point is not something you can check by trying every double. Dmitry Nadezhin proved it with a certified program in the ACL2 theorem prover (verify-todec; Result 20 in the paper). Over all doubles, 2V, 2Vℓ and 2Vr are either integers or more than 2−64 away from every integer. Together with the 2−68 error bound, this makes ro′(4V′) equal to the exact ro(4V), and likewise for Vℓ and Vr. The four checks then give exactly the answers they would give with infinite precision. The figure above prints, for each example, how far 2V actually is from an integer.

Two longs per table entry and three 64×126-bit multiplications replace the bignums. The multiplications share one g and run with no loop and no fallback path. In Java each product takes three 64-bit hardware multiplications (two of them multiply-high), and the lowest 64 bits of the product are never computed at all.

Putting it together

The whole algorithm

This follows OpenJDK's DoubleToDecimal, as a plain shortest printer (the paper's M = 1 variant). Every comparison is between 64-bit integers.

out = c & 1                       // 1: open interval
cb  = 4*c;  cbr = cb + 2
cbl = (c == 2^52 && q > -1074) ? cb - 1 : cb - 2
k   = floor(log10(width))           // q*661971961083 >> 41 (minus a constant at powers of two)
h   = q + floor(log2(10^-k)) + 2    // 2..5
g   = G[-k]                         // 126 bits, from the 617-entry table
vbl = rop(g, cbl << h)              // ro(4*Vl)
vb  = rop(g, cb  << h)              // ro(4*V)
vbr = rop(g, cbr << h)              // ro(4*Vr)
s   = vb >> 2                        // floor(V)
if s >= 10:
  sp10 = 10*(s / 10);  tp10 = sp10 + 10
  upin = vbl + out <= 4*sp10         // u' inside?
  wpin = 4*tp10 + out <= vbr         // w' inside?
  if upin != wpin: return (upin ? sp10 : tp10) * 10^k
t   = s + 1
uin = vbl + out <= 4*s               // u inside?
win = 4*t + out <= vbr               // w inside?
if uin != win: return (uin ? s : t) * 10^k
return (vb < 4*s+2 || (vb == 4*s+2 && s even) ? s : t) * 10^k

rop(g, cp): p = g*cp                // at most 186 bits
            return (p >> 127) | (bits 64..126 of p != 0)

Finally, strip trailing zeros from the result. Only a coarse hit can have them: 0.1, for example, comes out as 10000000000000000·10−17.

Java's Double.toString is the paper's M = 2 variant: it always prints at least two digits. So it tests s ≥ 100 and handles the two smallest subnormals specially, which is why Java prints 4.9E-324 where JavaScript prints 5e-324. Bolz's schubfach_64.cc is the plain variant shown here.
