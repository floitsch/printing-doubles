1 · Where we start

Dragon4 in one paragraph

Dragon4 (Steele & White, 1990) prints a double with four exact integers. The fraction r/s is the part of v still to be printed. m⁺/s and m⁻/s are the half-gaps to the neighbouring doubles: anything closer than that reads back as v.

Each step multiplies r and m± by 10 and takes the next digit d = ⌊r/s⌋, keeping the remainder in r. The loop stops as soon as the remainder is within m⁻ of 0 (then d already reads back as v) or within m⁺ of s (then d+1 does). The digit loop was never the problem. The problem was getting to the first digit. Dragon4 found the decimal exponent by multiplying by 10 once per decade: about 300 bignum multiplications for 1e308 or 5e-324, on integers more than 1000 bits wide.

Gay (1990) and Burger & Dybvig (1996) both kept the loop and replaced the walk with an estimate plus one exact check. Approach A explains why that estimate is never off by more than one. This page reads the code: first Burger & Dybvig's complete algorithm, then the route map of Gay's dtoa().

Remember

A positive double is v = f · 2e with an integer f < 253. For normal doubles 252 ≤ f; subnormals have e = −1074.

Its neighbours are one unit of f away, so any decimal within half a gap reads back as v. The exception is an exact power of two (f = 252): the double below is only half as far away as the double above.

A decimal exactly halfway between two doubles reads back as the one with the even f. So when f is even, the two boundaries themselves are allowed.

B&D: v ≈ 0.d₁d₂… × 10k dtoa: v ≈ d₀.d₁… × 10k, returns decpt = k + 1 Same digits; the two ks differ by one. Outputs below are shown as JavaScript would print them.

2 · Burger & Dybvig, PLDI 1996

The four-integer machine

Burger and Dybvig wrote the whole free-format printer in about thirty lines of Scheme (their Table 1 and Figure 3). The panel below is a JavaScript transliteration with the paper's names: r, s, m⁺ (mp) and m⁻ (mm). It has five parts:

  1. Initial integers (Table 1). Four cases set r/s = v exactly. A factor 2 is built in so that the half-gaps are whole numbers. In the power-of-two rows the gap below is half the gap above, so m⁺ = 2m⁻.
  2. Estimate. One line: k ≈ ⌈(e + len(f) − 1) · log102 − 10−10⌉ reads the exponent from the bit length alone. The result is either the true k or one less, never more.
  3. Scale by 10est in a single multiplication. The paper uses a table of 100…10325.
  4. Free fixup. If the top of the rounding interval, (r + m⁺)/s, already reaches 1, the estimate was one low. Then k goes up by 1 and the ×10 that digit generation would do first is skipped. So a low estimate costs nothing.
  5. Generate. d = ⌊r/s⌋ with remainder r. Test tc1 (keep d) and tc2 (take d+1). If neither holds, multiply by 10 and continue.

3 · Check it with a calculator

Two runs by hand

For 0.1 and 0.3, s is a power of two and the final comparisons involve single-digit numbers, so both runs can be checked by hand.

0.1: the estimate is low, and the fix is free

  1. 0.1 is stored as f = 7205759403792794, e = −56. Table 1, row 3: r = 2f = 14411518807585588, s = 257 = 144115188075855872, m⁺ = m⁻ = 1.
  2. The top bit sits at position e + 53 − 1 = −4, and ⌈−4 · 0.30103…⌉ = ⌈−1.204⌉ = −1. So est = −1: multiply r and m± by 10. Now r = 144115188075855880 and m± = 10.
  3. Fixup: r + m⁺ ≥ s (even already r > s), so the estimate was one low. k = 0, and the ×10 is skipped.
  4. d = ⌊r/s⌋ = 1, remainder r = 8. tc1: 8 ≤ m⁻ = 10 (f is even, so ≤). tc2: 8 + 10 ≥ s? No. Emit 1. Result: 0.1 × 100 = 0.1.

0.3: the remainder lands near s

  1. 0.3 is stored as f = 5404319552844595, e = −54 (odd f: the boundaries are excluded). r = 2f = 10808639105689190, s = 255 = 36028797018963968, m± = 1.
  2. The top bit is at −2, and ⌈−0.602⌉ = 0, so nothing is scaled. The fixup finds r + m⁺ < s, so est = 0 is right. Multiply by 10: r = 108086391056891900, m± = 10.
  3. d = 2 with remainder r = s − 4. tc1 fails badly. tc2: r + m⁺ = s + 6 > s. Emit d + 1 = 3. Result: 0.3, although the stored value is 0.29999999999999998889….

4 · Flip a rule, watch the output

Four rule switches

Each switch changes one line of the code panel. Each run is exact, so every output below is what the changed algorithm really prints.

1 · The reader rounds ties to even

The double nearest 1023 is 99999999999999991611392. Its upper half-gap is 223 = 8388608, so the top of its rounding interval is exactly 1023. Its f is even, so an IEEE reader turns "1e23" into this very double. With the switch on (the paper's setting), the machine may use the boundary and prints 1e23. With a strict interval it prints 9.999999999999999e22. Both read back correctly; the first is shorter. The strict rule is Steele & White's, and it is what dtoa's mode 1 does.

2 · Bug: symmetric gaps at powers of two

264 = 18446744073709551616. The double above is 4096 away, the one below only 2048. The correct machine prints 18446744073709552000. The bug skips the power-of-two rows of Table 1 and uses a lower half-gap of 2048 instead of 1024. That lets 18446744073709550000 through, 1616 below v, which reads back as 18446744073709549568 = 264 − 2048: the wrong double. 2−44, 2−25 and 265…268 break the same way.

3 · Choose k from v, not from high

B&D pick k so that even the top of the rounding interval is below 10k. For 1e23 that top is 1023 itself (and allowed), so k = 24. The first quotient is then 0, and tc2 turns it into 1: no carry, ever. dtoa picks k from v. With this switch the machine does the same: k = 23, the first digit is 9, tc2 asks for 9 + 1, and a carry has to ripple left. That is dtoa's round_9_up. It happens for 298 of the 632 powers of ten from 1e-323 to 1e308: exactly those whose double lies below 10n.

4 · The final-digit tie rule

2237844659592604.25 is a double, and its neighbours are 0.25 away. Both 2237844659592604.2 and …604.3 read back as it, and both are exactly 0.05 away. B&D's Figure 1 breaks such ties upwards and prints …604.3. dtoa and JavaScript pick the even digit and print …604.2. Both are correct shortest outputs. This is a choice, not a bug, although ECMAScript's Number.prototype.toString requires the even one.

5 · Stated carefully

What the machine promises

With the switches in their default positions, B&D's output is

  • inside the rounding interval, so it reads back as v;
  • shortest: no string with fewer digits reads back as v;
  • when both d and d+1 would do, the nearer of the two, with ties going up.

The original paper also claimed correct rounding (its Theorem 4). The corrected version of the paper, with corrections from Raffaello Giulietti (2006), states that Theorem 4 is false because its definition was too strong. Only the three properties above are claimed here. They are all the tests on this page rely on: over 20,000 random doubles, the machine agrees with Number#toString except on exact ties like switch 4.

8 · Guided tour

Seven routes worth taking

  • The plain route. ds gives k̂ = −1, which is right. One factor of 2 is cancelled. The first quorem digit is 2, j1 > 0 sends it out through exit C, and it prints "3".
  • Every special branch in one number. ds = 23.00327 gives k̂ = 23, which is too big for the tens[] check, so k_check is set. After scaling, b < S lowers k to 22. The first digit is 9 with j1 == 0 and an even mantissa, so exit A leads to round_9_up, which carries to "1" with decpt 24.
  • The biggest integers. 324 factors of 2 are cancelled, and S still has 764 bits (1076 without cancelling). The first digit is 4, both exits hold, and 2b > S rounds it up to "5".
  • The tangent overshoots (k̂ = 3) and a plain double comparison with tens[3] = 1000 repairs it without any bignum.
  • A small integer (be ≥ 0, k ≤ 14). Exact double arithmetic prints it; no bignum is ever built.
  • quorem's guess from the top words is 0, and its single correction step makes it 1.
  • The longest ride: 17 turns of the digit loop, with S at 732 bits instead of 1025.

Two notes for readers of the source. Mode 0's shortest-digit logic lives in the leftright branch. The floating-point try_quick shortcut that Gay's paper describes is only for modes 2–5 with few digits; mode 0 never takes it.

9 · Before you open dtoa.c

The dtoa.c you download today

Since the change dated 2016-04-29, netlib's dtoa.c defines USE_BF96 by default whenever 64-bit integers are available. Mode 0 then first computes k exactly from a table and tries to produce the digits with 64-bit integers and a 96-bit approximation of 10−k that carries its own error bound. Only when that approximation cannot decide does it jump to Fast_failed1, which rebuilds b2, s2, b5, s5 and rejoins the bignum path at the bookkeeping station (the dotted line on the map). In that build the small-integer path and the tens[]/k_check repair are compiled out. Compile with -DNO_BF96 to get the classic route shown here. Both builds print the same digits.
