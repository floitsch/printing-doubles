One primitive, three programs

Russ Cox’s shortest printer, fixed-width printer and parser all call the same function: uscale. It multiplies by a power of ten and hands back the result unrounded. This page opens it up: a 192-bit product in three 64-bit words, why the table’s error cannot reach the answer, and why one multiply is almost always enough. Then it runs the real code with every variable lit up.

1 · The data type

Two extra bits

Round too early and you round wrong. Keep every digit and you pay for bignums. Cox keeps exactly two bits more than the integer.

An unrounded number ⟨x⟩ is the integer part of x, followed by a ½ bit (is the fraction at least one half?) and a sticky bit (is there anything else left over?). In one line: ⟨x⟩ = ⌊4x⌋ | (4x ≠ ⌊4x⌋), stored in an ordinary uint64. It is written n.0, n.0+, n.5 or n.5+, where “.5” means “the ½ bit is set” and “+” means “and a bit more”.

Every rounding rule is now “add a constant, shift right by two”: +0 for floor, +1 for round-half-down, +2 for round-half-up, +3 for ceiling, and +1 plus the integer’s low bit for round-half-to-even (so 6.5 goes down to 6 and 7.5 goes up to 8). 6.25 and 6.001 get the same code: the ¼ bit is simply folded into the sticky bit, because no rounding rule needs it.

Three more one-liners complete the type:

  • nudge(±1) adds ±1 to the code: it behaves as if an infinitesimal were added or subtracted. ⟨7.0⟩.nudge(−1) is 6.5+, whose floor is 6, not 7. This is how the printer will exclude an interval endpoint.
  • div(d) is u/d | u&1 | (u%d ≠ 0): the sticky bit sticks. ⟨15.4⟩ = 15.0+ (61); 61/6 = 10 remainder 1, so the result is 11 = 2.5+, which rounds to 3. Rounding first would give 15/6 = 2.5 and then 2. (15.4/6 = 2.57, so 3 is right.)
  • rsh(1) is the same idea for a shift by one bit. The parser needs it once.

Want to drag a point along a line and watch it snap into these four zones? Approach A builds the idea visually. This page assumes the table above and heads into the machine.

2 · The primitive

One function, called by everything

The primitive is

uscale(x, e, p) = ⟨x · 2e · 10p⟩

for a 64-bit integer x, normally left-justified (top bit set). That one call is where binary meets decimal. Here is where each of Cox’s three conversions uses it (highlighted); everything around it is a few lines of integer bookkeeping:

Short(f): shortest digits

pre  := prescale(e, p, log2Pow10(p))
dmin := uscale(min, pre).nudge(+odd).ceil()
dmax := uscale(max, pre).nudge(-odd).floor()
…
d = uscale(m, pre).round()

Given m, e, it picks the decimal exponent p.

FixedWidth(f, n): n digits

p = n - 1 - log10Pow2(e+63)
u := uscale(m, prescale(e, p, …))
d = u.round()
if d >= 10ⁿ { d = u.div(10).round() }

Given m, e and n, it picks p.

Parse(d, p): decimal → double

e := min(1074, 53-b-lp)
u := uscale(d<<(64-b), prescale(…))
… one rsh(1) if 54 bits came out
return pack64(u.round(), -e)

Given d, p, it picks the binary exponent e.

Printing knows e and chooses p; parsing knows p and chooses e. Each picks the missing exponent so that the integer part of the result is exactly the integer it wants (about 17 decimal digits for Short, n digits for FixedWidth, a 53-bit mantissa for Parse), and each rounds afterwards, however it likes. If uscale is exact, all three programs are correct almost by inspection. So the hard question is: how does uscale get an exact ⟨⟩ without bignums? Sections 3 to 7 answer that. Section 8 then runs the three programs.

3 · The ingredient

A table of 128-bit powers of ten

Multiplying by 2e is just a shift. The 10p needs a table. Most powers of ten have no finite binary form (10−1 = 0.000110011001…₂ repeats forever), so Cox stores each one as a 128-bit mantissa, rounded up:

pm = ⌈10p / 2pe⌉ ∈ [2127, 2128)
pe = ⌊log₂ 10p⌋ − 127

So 10p ≈ pm · 2pe, and pm is too big by some ε₀ with 0 ≤ ε₀ < 1 (in units of pm’s last bit). The table covers p ∈ [−348, 347]; the three algorithms need [−343, 341]. Since 10p = 5p · 2p, only the 5p part needs bits: for 0 ≤ p ≤ 55 it fits in 128 bits and the entry is exact; for 0 ≤ p ≤ 27 it even fits in the top 64 bits.

4 · The product

Where the error can’t reach

A 64-bit x times a 128-bit pm is a 192-bit product. Picture it as three 64-bit words:

x · pm = [ hi | mid | lo ]

prescale picks a shift s = −(e + ⌊log₂ 10p⌋ + 3) so that, error aside, hi >> s is ⌊4 · x · 2e · 10p⌋: the integer, the ½ bit and the ¼ bit (which becomes the sticky slot). Everything below the cut (the low s bits of hi, all of mid and lo) only has to answer one question for the sticky bit: is any of it nonzero?

Now the error. pm is too big by ε₀ < 1, so the product is too big by x · ε₀ < x < 264. The whole error fits in the bottom word. So Cox never looks at the bottom word: he throws it away (in fact never computes it) and takes the sticky bit from the low bits of hi and mid. Compare the true product with the computed one:

This is Cox’s first, straightforward uscale. It computes the top two words exactly (two 64×64-bit multiplies) and ignores the bottom one:

hi, mid := bits.Mul64(x, c.pm.hi)        // top 128 bits of x·pm.hi
mid2, _ := bits.Mul64(x, c.pm.lo)        // low half = bottom word: dropped
mid, carry := bits.Add64(mid, mid2, 0)
hi += carry
sticky := bool2(mid != 0 || hi&((1<<c.s)-1) != 0)
return unrounded(hi>>c.s) | sticky

In the 1e23 frame the true product ends in 128 zero bits: the upper midpoint of that double is exactly 1023. The computed bottom word is pure error, but it is never looked at, the middle reads zero, and uscale correctly reports an exact 10000000000000000.0, no “+”. That exactness decides the output: the printer may use this endpoint, and prints 1e23.

5 · The only danger

A single 1 bit is a firewall

The error changes the bottom word freely. It can change a higher word in only one way: a carry out of the bottom word. A carry turns 1s into 0s from right to left until it meets a 0, which becomes a 1, and stops. So if a carry ran through the whole middle and into the top word, it left the middle all zeros. Turn that around: if the computed middle contains a single 1 bit, no carry reached the top, and the top is right. That 1 also proves the result is inexact, so the sticky bit is right too.

Try it on a 12-bit toy product: 4 top bits, 4 middle bits, 4 bottom bits. The error is at most 15, so it “fits in the bottom word”, just like the real one.

Borrow is the same with 0s and 1s swapped. In section 7 the machine will see a value that is slightly too big and will have to subtract. A borrow turns 0s into 1s until it meets a 1. So it can reach the top only if the bits the machine sees in between are all 0. In both directions, the danger sign is the same: all zeros between the kept bits and the bottom word.

6 · The guarantee

Proved, not hoped

So uscale is right whenever the middle is nonzero for inexact results. (For exact results the true bits below the cut are zero; the error cannot carry out of the bottom word, and the middle correctly reads zero.) Is the middle ever all zero for an inexact result? Cox’s proof post settles it, case by case:

The proof ladder
  1. p ∈ [0, 27]: nothing to prove. 5p < 263, so the table entry is exact (ε₀ = 0) and the product has no error at all.
  2. p ∈ [−27, −1]: the fraction can’t hide. Here the product is x/5k (k = −p) times a power of two. If that is not an integer, its fractional part is a multiple of 1/5k, at least 5−27 > 2−63 away from 0 and from 1. A gap that wide shows up as a middle of at least 2, far from both all-zeros and a wrap-around.
  3. p ≤ −28 and p ≥ 28: checked by program. No neat argument exists. Cox wrote an Ivy program that visits every table entry and, with a modular-minimum search in the spirit of Paxson’s and Peters’ algorithms, finds the smallest middle any input can produce. Result: the middle is at least 2 for every 55-bit x when the middle is at least 66 bits wide (printing), and for every 64-bit x when it is at least 73 bits wide (parsing).

Why the fine print about widths? Because the claim is false in general. Here is the proof post’s counterexample: an arbitrary 64-bit x times the entry for 1062, split into three plain 64-bit words.

The carry went all the way through: the computed middle is all zeros, and the computed top word is one too big. Short never passes such an x: its inputs have at most 55 significant bits, and the widths it uses leave a longer middle. Parsing uses all 64 bits but needs only 55 bits of output, which leaves a middle of at least 73 bits. For exactly those widths, the program proves the firewall is always there.

7 · The optimization

Usually, one multiply

The straightforward version always does two 64×64-bit multiplies. Cox’s real one usually does one. The trick is to store each entry differently: as hi·2⁶⁴ − lo instead of hi·2⁶⁴ + lo. Now hi alone is the top half of pm rounded up, and x · hi alone gives a [hi | mid] that is slightly too big. The true value is x · hi · 2⁶⁴ − x · lo, and x · lo is less than one unit of hi. So the true hi is either hi or hi − 1: at most a borrow.

And a borrow can reach the kept bits only through zeros. If any of the s bits about to be dropped from hi is a 1, the borrow dies there. The kept bits are right, and that 1 also proves the result inexact, so the sticky bit is 1. One multiply, done. Only if those s bits are all zero does the code pay for the second multiply:

func uscale(x uint64, c scaler) unrounded {
	hi, mid := bits.Mul64(x, c.pm.hi)           // the one multiply
	sticky := uint64(1)
	if hi&(1<<(c.s&63)-1) == 0 {              // no 1 bit among the s dropped bits?
		mid2, _ := bits.Mul64(x, c.pm.lo)     // top half of x·lo only
		sticky = bool2[uint64](mid-mid2 > 1)
		hi -= bool2[uint64](mid < mid2)       // the borrow
	}
	return unrounded(hi>>c.s | sticky)
}

Why “> 1” rather than “≠ 0”? Only the top half of x · lo is computed; its bottom half would subtract at most one more unit from mid. So a difference of 1 means the true middle is 0: exact. The proof shows an inexact middle is never 0 or 1, so the test cannot be fooled.

Why is the check so rarely needed? The dropped bits of hi are all zero only about once in 2s. And Short’s calls share the table entry but have different x, so at most one of them usually falls on the slow path. Measure it yourself:

Cutting the corner is the classic 64-bit trap. Grisu works with 64-bit powers of ten and is therefore sometimes unsure (Grisu3 detects it and falls back to a slower algorithm). Cox’s conditional second multiply is what turns “usually right” into “proved right”, for the cost of about one multiply in seventy.

8 · The programs

The code, with the lights on

Remember

A double is m · 2e. Every real number closer to it than to its neighbours reads back as that double. The midpoints to the two neighbours bound this rounding interval; they belong to it when the 53-bit mantissa is even (ties go to even). At a power of two the neighbour below is only half as far away, so the interval is lopsided (“skewed”).

Short scales the two midpoints, not the double, with a p that makes the interval between 1 and 10 units wide. Then dmin = ceiling of the lower end and dmax = floor of the upper end bound the valid integers, and a width under 10 means at most one of them ends in 0. Three cases: a valid integer ending in 0 exists (use it, drop the zeros); exactly one valid integer; or several, in which case a third uscale scales the double itself and rounds. Approach A draws this decimal window; here you watch the code do it.

What to try

  • 0.3 and 0.1+0.2 are neighbouring doubles. They share a midpoint: 0.3’s ⟨max⟩ is 0.1+0.2’s ⟨min⟩. 0.3 finds an integer ending in 0; 0.1+0.2 has six valid integers, none ending in 0, and needs the third call.
  • 2^89 takes the skewed branch. Its nearest 16-digit decimal, …901 (the double is 6189700196426901.37… · 1011), lies outside the interval; only …902 reads back. That is why Short scales the endpoints instead of the value.
  • 5e-324, the smallest subnormal, sets z = 63: the whole interval is 2.47 to 7.41 · 10−324, one digit, and you can check every step by hand.
  • 1e23: the upper end lands exactly on 10000000000000000.0, and the mantissa is even, so that end counts. Switch to Parse and read “1e23”: the scaled value is an exact tie, ⟨5960464477539062.5⟩, and round-half-even picks the even mantissa.
  • FixedWidth: π at 15 digits gives ⟨314159265358979.0+⟩. 1.125 at 3 digits is an exact tie ⟨112.5⟩: Go and C print 1.12, JavaScript’s toPrecision rounds ties up to 1.13. The unrounded result lets the caller pick. 9.999999 at 3 digits rounds to 1000, one digit too many, so the code divides the unrounded value by 10.

10 · Lineage

Whose ideas

Cox presents unrounded scaling as a synthesis, and says so in detail in “Floating-Point Printing and Parsing Can Be Simple And Fast”:

  • The sticky bit is Len Harding’s, probably from the late 1960s; its first hardware was the BCC Model 1 in 1970. Unrounded numbers are that idea turned into a data type.
  • 128-bit tables are enough for exact conversion: Hanson (Apple, 1990s), then Hack (the first proof, for parsing, 2004), Nadhezin and Giulietti, and Adams’s Ryū. Eisel and Lemire’s parser uses the same idea.
  • Checking whether a carry could have mattered goes back to Slishman (IBM, 1990), who computed 16 extra bits and fell back to bignums when they were all 1s: his table was rounded down, so the danger sign was inverted.
  • The shortest-printing structure, including “with the right p, at most one valid decimal ends in 0”, is Giulietti’s Schubfach. Schubfach even computes a special case of unrounded scaling.
  • trimZeros, the multiply-by-inverse way to strip trailing zeros, is from Jeon’s Dragonbox.
  • New in Cox’s version: the unrounded type as the common interface for all three conversions, the rounded-up hi that usually saves the second multiply, and a proof, checked by program for every table entry, that this fast uscale is exact for the input widths the conversions actually use.

Sources: the post above, the proof post “Fast Unrounded Scaling: Proof by Ivy”, and the code at github.com/rsc/fpfmt (fpfmt.go, pow10gen.go, commit ec108cb; BSD-style license, © The Go Authors).
