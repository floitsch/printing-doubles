Pocket Ryū, then try to break it

First, run all of Ryū on a 16-bit float, where every number fits on a phone calculator. Then shrink its table of powers of five until it breaks, and see why the real table never does.

Learn the algorithm on a format small enough to check by hand. Then answer the safety question, “why is there no fallback?”, by letting the reader hunt for the inputs that would need one.

01 · The plan

Three integers, one multiply, then delete digits

Ryū (Ulf Adams, PLDI 2018) prints the shortest decimal that reads back as the same double, and among those the closest one. It does not produce digits from left to right. Instead it does four things:

  1. Make three integers. Write the value and the two ends of its rounding interval as integers, all counted in the same small power of two.
  2. Change the unit. Count the same three points in a decimal unit 10e10 instead. Rounding down to whole units takes one multiplication by a stored power of five and one shift.
  3. Delete digits. Remove the last digit of all three integers together, as long as a shorter number still fits between the outer two.
  4. Round. The last digit removed from the middle integer decides between it and the next integer up.

For a double these are 17–19-digit integers and 125-bit constants, too big to check by hand. So we run the same steps on half precision first, where every number fits a phone calculator.

Remember: binary16 (half precision)

16 bits: 1 sign bit, 5 exponent bits (bias 15) and 10 fraction bits. A normal half is (1024 + fraction) × 2exponent − 25. Exponent field 0 means subnormal: fraction × 2−24. Field 31 means ∞ or NaN.

The largest half is 65504 and the smallest is 2−24 ≈ 5.96·10−8. That is about three significant decimal digits.

The rounding interval of a value runs from the midpoint with its lower neighbour to the midpoint with its upper neighbour. Every real number in between reads back as this value. A number exactly on a midpoint goes to the neighbour with the even significand.

03 · Rounding

Three rules pick b or b + 1

After the deletions, b is the value rounded down to the final unit, so the answer is either b or b + 1. The code decides with one line, output = vr + (outside || lastDigit ≥ 5), which combines three rules:

  1. Round up when the last deleted digit is 5 or more. Example: half 0.1 above (digit 9).
  2. Except on an exact tie, which rounds half to even. The last deleted digit may be 5 with only zeros deleted before it, and with nothing lost in the multiply. Then the value sits exactly halfway between b and b + 1. If b is even, the code treats the 5 as a 4 and keeps b. Example: prints 0.1562.
  3. Always round up when b is outside the interval. a is the lower bound rounded down, so when b = a, b can sit below the real lower bound. Then b is not allowed and b + 1 is. The one exception is when a lands exactly on the bound and the bound itself is allowed. This rule matters for powers of two, whose lower neighbour is twice as close. Example: is an exact tie with an even b = 1562. It still prints 0.01563, because 0.01562 is below its interval.

The ends of the interval are allowed only when the significand is even, because a reader rounding ties to even would then map the midpoint back to this value. When an allowed lower bound is an exact decimal, it can even be the answer: prints 4110, because a = 4110 is exact and allowed. In that case Ryū keeps deleting while a ends in 0 (the second loop in d2s.c). An exact upper bound that is not allowed is excluded by subtracting one from c at the start ().

04 · Same steps, binary64

A double only changes the sizes

Here is the same card, set to binary64. Flip the switch on either card to run any value in the other format. The steps and branches are identical. Only the numbers are longer.

What actually changes:

  • Sizes. m2 has 53 bits and e2 runs from −1076 to 969. The three counts have 17–19 digits, and up to 17 digits get deleted (0.3 needs 17 deletions; a typical random double needs 1–3).
  • The table. A half never needs more than 59 = 1,953,125, which is 21 bits, so every pocket constant is exact. Halves of 4096 and above have q = 0, so they need no constant at all. A double needs powers up to 5325 (755 bits) and reciprocals down to 1/5290. d2s.c stores 125-bit versions: the top bits of 5i, truncated, for e2 < 0 (326 entries), and ⌊2k/5q⌋ + 1, the reciprocal rounded up, for e2 ≥ 0 (342 entries). Each entry fills two 64-bit words.
  • The multiply. mX fits in 64 bits and the constant takes two words. So each of the three counts costs one 64×128-bit multiply that keeps the high part of the product, plus a shift.
  • Two shortcuts, same results. d2s.c prints integers in [1, 253) directly. In the common case where neither exactness flag is set (about 99.3% of doubles, per the source), it deletes two digits at a time first.

The truncated table raises the one question that halves never do: is every floor still exact? If it is not, the output can be wrong, and Ryū has no fallback to catch it.

05 · Why no fallback?

When can a truncated constant hurt?

Ryū never checks its floors. There is no error bound, no retry and no big-number fallback. For that to be safe, a 125-bit constant must give the same floor as the exact power of five for every double. First, look at which way the error goes:

A floor goes wrong only if some exact scaled value lands inside the thin strip on the dangerous side of an integer. An exact integer is never at risk. With a truncated 5i, the product can only be an integer when 2q divides mX, so q ≤ 54. For those exponents, 5i has at most 61 bits and the entry is exact anyway. With a rounded-up reciprocal, the product is just pushed a little above the integer.

So the question is not about rounding any more. It is number theory: how close can m · 2x / 5y get to an integer, over all 253 significands of one exponent? That differs from exponent to exponent and has to be computed.

06 · Shrink the float

Check every bfloat16

For a small format you can simply try everything. bfloat16 has an 8-bit significand and the same exponent range as float32. Run Ryū's own q and e10 rules on it, with a B-bit table in the same shape as d2s.c's. Then compare all three floors of every positive finite value against the exact floors: 97,917 floors in all.

A few bits past “usually fine”, exactly one value is still wrong, and one more bit fixes it. For binary64 there are 264 values, far too many to try. So how do you find its lone survivors?

07 · Needle in a haystack

Random testing versus a hunt

Pick a table width B for binary64. Then try to break Ryū in two ways:

  • Test random doubles. Draw 100,000 random bit patterns, so every exponent is equally likely, and compare all three floors with exact arithmetic.
  • Hunt adversarially. For each of the 2,047 binary exponents, a wrong floor needs the residue (mX · 2s) mod 5q, or (mX · 5i) mod 2q, to land in a small window next to the modulus or zero. Finding the smallest x with (a · x) mod M inside a window is a recursion in the style of Euclid's algorithm, so the hunt jumps from candidate to candidate without scanning. Every candidate is then checked with exact arithmetic. This is our reproduction of the idea, not the paper's tool.

Random testing stops finding anything at about 77 bits: at that width a wrong floor is too rare to show up in 100,000 draws. The hunt keeps finding needles for another 46 bits. At 112 bits more than half of all exponents still have one, and the last one disappears only at 124 bits. Some needles are harmless because the digit deletion throws the wrong digit away. Others change the output (click one), and some produce a string that reads back as a different double.

08 · What is proven

124 bits by proof, 125 in the code

The paper does not search for needles. Its lemmas (Section 3.2) show that the floors are exact when 2k is large enough compared with the smallest (or largest) value of a modular product, (w · 5i) mod 2q or its e2 ≥ 0 counterpart, over every possible w. It computes those extremes per exponent with minmax_euclid, an extension of the extended Euclidean algorithm. The algorithm is sublinear and may return a slightly conservative bound. The resulting widths (Figure 4) are B0 = B1 = 124 bits for Float64, 60 and 63 for Float32, and 15 and 21 for Float16.

d2s.c uses 125-bit constants (DOUBLE_POW5_INV_BITCOUNT = DOUBLE_POW5_BITCOUNT = 125) stored in pairs of 64-bit words. That is one bit more than the proven minimum.

Our hunt agrees with the paper from the other side. The last needles it finds are at 123 bits for e2 ≥ 0 () and at 122 bits for e2 < 0 (). At 124 and 125 bits it finds nothing in any exponent. That is evidence, not a proof. The guarantee is the paper's lemma.

What “no fallback” buys. Grisu works with 64-bit approximations and error bounds, and gives up on about 0.5% of doubles, which then need a slow exact algorithm. Ryū pays for 128-bit products and a table of about 10 KB. In exchange its floors are exact by construction, so the digit deletion and rounding can be plain integer code with no uncertainty left to handle.
