1 · The trick

Ask small questions, get exact answers

The number 6.62607015 × 10−34 is stored as f · 2−163. To read off its decimal digits exactly, you would compute v · 1050 = 8f · 1050/2166. The fraction 1050/2166 has a 167-bit denominator, so the exact route needs big integers.

Toothless never computes that product. Every decision it makes is a yes/no question with one shape: is the small fraction a/b above or below α = 2ek/10k? For example, “is the prefix 66260701 · 109 already above the lower end of the rounding interval?” becomes “is 66260701000000000 / 61977679189084292 ≥ α?”. Both parts of every such fraction stay below 259.

Toothless answers each question against a cached stand-in num/den instead of α. Both parts of the stand-in are below 263. The stand-in is not exact: for this number it is 1.3 × 10−36 (relative) below α. But it was chosen with continued fractions so that no fraction whose parts are below 262 lies between the stand-in and α. A question fraction is far too small to fit into that gap. So “above num/den?” always has the same answer as “above α?”. Only a question that lands exactly on num/den can’t be settled this way. For that case, two tag bits in the table say which side of α the stand-in lies on.

This “nothing lives in the gap” argument is what sets Toothless apart. Grisu and Errol bound their approximation error, then fall back or special-case inputs when a decision lands inside that bound. Toothless picks its stand-in so that no decision can land there at all. Approach A, Nothing lives in the gap, builds this picture with a toy float. This page follows one real double through the real code.

Status. Toothless is unpublished. The mechanism is argued in an unfinished 2017 draft and checked numerically, not proved. The draft’s proofs have TODOs, and a few steps exist only in code. The claims ledger at the end lists what is argued, what this page re-checks, and what is still open.

Remember

A positive double is exactly v = f · 2e with an integer significand f (53 bits for normal numbers). Every real number closer to v than halfway to its neighbours reads back as v. That is the rounding interval [m−, m+]. Its ends count only when f is even, because ties read back to the even significand.

For a power of two the neighbour below is only half as far away, so the interval is lopsided. Shortest printing picks the decimal in the interval with the fewest digits. If several decimals have that length, it picks the one closest to v.

2 · The code

Follow one double through continued.c

Pick a number and press Step. The ←/→ keys also work while the figure has focus. The stepper runs a line-by-line BigInt port of the reference implementation, bench/continued.c, with its real cache, bench/fraction_values.h. The cache has 325 entries, and their tag bits are kept as stored. The log below the card collects every comparison the code makes. Each comparison also gets the answer that the exact α would give.

Things to notice

The margins are huge compared with the gap. For most inputs the tightest question still lies 10−17 or so away from α, while the stand-in is within 10−36. The hard case preset, 3.294312317590731 × 10−79, is the exception. Its lower boundary is 3.29431231759073099999999999999999813…e−79, so the 16-digit answer clears it by only 5.7 × 10−34 (relative). A 64-bit approximation of the power of ten has an uncertainty near 10−19 and cannot decide that question. Toothless decides it exactly, because even this margin is 105 times the width of the gap.

The margin is not the proof. A big margin shows that a single question was safe. The guarantee for all questions comes from the empty gap: a question fraction with parts below 259 can’t be inside it, however close it gets to α. The badge on each row checks exactly that.

Negative exponents use the reciprocal. The table only stores 2e/10i for i = 0…324, a value in (½, 1]. For numbers below 1 the code needs 10n/2e instead. It swaps numerator and denominator, and with them the “lower” and “higher” tags. Entries 0…27 are exact (527 < 263), so doubles from about 1.5 × 10−11 to 9 × 1043 never touch an approximation.

3 · The cache

Where the 63-bit fractions come from

Each table entry comes from the continued fraction of its exact ratio αi = 2⌊i·log210⌋/10i. Cutting the continued fraction after each term gives a convergent: a fraction that approximates α very well for its size. Convergents alternate around α, and their denominators grow at each step by a factor of about the next term. The Planck example uses entry 50, and its continued fraction contains the term 479. That term makes the denominators jump from 55 bits straight to 64 bits, past the 63-bit limit.

Between the 55-bit convergent h30/k30 and the 64-bit one lie the semiconvergents (c·h30 + h29)/(c·k30 + k29) for c = 1…478. Each one is closer to α than the one before. The table stores c = 329, the last one whose parts fit below 263, tagged “higher”. It and the 55-bit convergent are Farey neighbours: their cross-product differs by exactly 1. So any fraction strictly between them has a denominator of at least the sum of their denominators (the standard Farey argument), and that sum is above 263. That is the empty gap. The ledger re-checks it for every entry.

4 · Starve the cache

Rebuild the cache with fewer bits

How much of the 63-bit budget is needed? Rebuild all 325 entries with fractions whose parts are below 2B. The page uses the continued-fraction bracket of each α and keeps whichever endpoint is closer, which takes a few milliseconds per table. Then run real hard cases through the same code. They were found by a targeted search. Random testing would not find them, as the button below shows.

With 50-bit fractions, 3.294312317590731 × 10−79 prints with one digit too many. 3.7299018480438463 × 10228 prints as a 16-digit string that reads back as a different double. With 52 bits, 6.1359116592542813 × 10−266 fails to round-trip. From 54 bits on, all of these pass. Yet the 50-bit table passes 100,000 random doubles without a single failure. Random testing is weak evidence here. Failures need a question fraction that lands in the gap, which is a vanishingly thin target. Load a failing case into the stepper to see which question lands in it: that row turns red.

The separation argument itself only needs B ≥ 59, one bit more than the largest question. From 59 bits on, any fraction inside a gap has a part of at least 259. Between 54 and 58 bits, no failure is known to this page, but nothing guarantees there isn’t one.
