Żmij: the decision on a dial

Żmij multiplies once and then asks three yes/no questions about a single 64-bit fraction. Wrap that fraction around a clock face and all three questions become one picture: an arc, twelve o’clock, and ten tick marks.

Approach A explains the decision in pictures. A fraction dial with an odometer shows one number. A decision map then shows every double at once, which is why the result is always right. The machine words stay underneath as captions.

1 · The idea

Zoom one notch too far

Shortest printing asks: of all decimals that read back as this double, which has the fewest digits? If several do, pick the nearest.

Remember

A positive double is v = m · 2e, where m is a 53-bit integer. Neighbouring doubles are one ulp = 2e apart.

Every real number within half an ulp of v reads back as v. That is the rounding interval, v ± 2e−1. Its ends count only when m is even (ties go to even).

At an exact power of two, the neighbour below is only half as far away, so the interval is lopsided.

Most algorithms scale v by 10−k so that it becomes a 17-digit number, then work out shorter candidates from it. Żmij scales by one more power of ten, 10−k−1. After that single multiplication:

  • the integer part I already is the 15- or 16-digit short answer, or its neighbour I + 1 is;
  • the fraction F says where v sits between I and I + 1;
  • the half-width h of the rounding interval, at this scale, comes from the same power-of-ten constant by a shift. No second multiply is needed.
c = m·2e·10−k−1 = I + F h = 2e−1·10−k−1

How k is chosen. Take k = ⌊e·log102⌋, so that 10k ≤ 2e < 10k+1. At this scale one ulp becomes u = 2e/10k+1, somewhere between 0.1 and 1. Two things follow:

  • h = u/2 always lies in [0.05, 0.5);
  • c = m·u lies between 252·0.1 ≈ 4.5·1014 and 253 ≈ 9.007·1015, so I has 15 or 16 digits.

You can check this by hand with 0.3. It is stored as m = 5404319552844595 (odd) and e = −54. That gives k = ⌊−54 × 0.30103⌋ = −17, so we multiply by 1016:

  • c = 2999999999999999.8889776975…
  • h = 2−55·1016 = 0.2775557561…

2 · The picture

One turn = one step of the short grid

Wrap the number line around a clock face so that one full turn is one unit of 10k+1:

  • the odometer in the middle counts whole turns: it shows I;
  • the dot is the fraction F, drawn as an angle;
  • the blue arc is the rounding interval, F ± h;
  • twelve o’clock is where the short grid lives: every whole number of turns is a 15–16-digit decimal;
  • the ten tick marks are the tenths of a turn, one decimal digit finer.

Three questions, asked at once

  1. Forward past 12: round up. If the arc reaches the next whole turn, then I + 1 lies inside the interval. In the machine, F and h are 64-bit words. “Reaches a full turn” means F + h overflows 64 bits, so the carry out of the add is the answer. The code adds that carry straight into I (integral += round_up), and the odometer rolls over. For 0.3 it rolls from 2999999999999999 to 3000000000000000; the zeros drop off, and out comes 0.3.
  2. Back past 12: keep I. If F < h, the arc reaches back past the last whole turn, so I itself reads back. That is what happens for 0.1: F = 0.0555…, h = 0.0694….
  3. Neither: one more digit. Then no 16-digit decimal fits, and the answer has 17 significant digits: I followed by the digit of the nearest tick. The code computes it as hi64(10·F + 263 + 6), that is, 10·F rounded to the nearest integer. The small + 6 makes up for the truncated F. Note that it rounds rather than truncates: for 1/7, F = 0.492, so the nearest tick is 5, not 4.

The three answers don’t depend on each other, so the CPU computes all three in parallel from the same two words and then picks one. There are no loops and no divisions.

3 · Why it is always right

The arcs tile the circle

Step from a double to the next one. The dot moves by exactly one ulp, u = 2h, so each arc starts exactly where the previous one ended. The figure below draws consecutive doubles as a spiral, so you can see the arcs meet end to end. Two facts about the arc width 2h finish the argument:

  • 2h < 1 turn, so an arc can reach past 12 in at most one direction. At most one 16-digit decimal fits, and the flags never disagree.
  • 2h ≥ 0.1 turn, the tick spacing, so the tick nearest to the dot is at most 0.05 turn ≤ h away. It is always inside the arc. Seventeen digits always suffice, and the nearest one is always allowed.

For odd m, the ends of the interval are open; for even m they are closed. The machine applies this by adding 1 to h when m is even. That makes both tests inclusive: an arc that ends exactly on 12 then counts as reaching it.

4 · Knife edges

Three cases that land exactly on a line

: the arc ends on 12

Here every number is exact and can be checked by hand:

  • 1023 is not a double. The nearest one is 99999999999999991611392, with m even and e = 24.
  • k = 7, so we multiply by 10−8: c = 999999999999999.91611392 and h = 0.08388608.
  • F + h = 1 exactly, so the arc ends precisely on 12.

Because m is even, the end of the interval counts, and 1e+23 reads back. In the machine, F = 0xea86711dcf73c620 and h = 0x15798ee2308c39df + 1. They add up to exactly 264, and only that +1 makes the add carry. Load it and tick “pretend the significand is odd”. The carry disappears and the output becomes 9.999999999999999e+22. That string still reads back, but it is not the shortest. The +1 carries the tie rule.

: halfway between two ticks

Here F is exactly 262, a quarter turn, so 10F = 2.5. The rounding constant 263 would round that up to 3, but ties must go to the even digit, 2. The code has one special case for this, if (fractional == 1ull << 62) digit = 2. Only F = ¼ and F = ¾ give an exact half. For ¾, 7.5 rounds up to 8, which is already even. Output: 70368744177664.12.

: a lopsided arc

For a power of two the lower neighbour is twice as close, so the arc reaches only h/2 backwards. Żmij sends these 2,046 inputs down a separate, rarely taken path:

  • k comes from ¾·2e;
  • “keep I” uses F < h/2;
  • the digit is clamped into the arc: max(round(10F), ⌈10(F − h/2)⌉).

For 2−1017 the nearest tick, 4, lies outside the short side of the arc, so the digit is bumped to 5. Output: 7.120236347223045e-307. The correctly rounded …3044 would not read back. 26 of the 2,046 powers of two need this bump.

5 · Every double at once

Every double on one square

The decision depends on just two numbers, F and h. So the whole decision can be drawn once, as a map. Across the square is F, a fraction of a turn. Up the square is h, and it only ever takes values in [0.05, 0.5):

  • Left of the diagonal F = h, the arc reaches back past 12: keep I.
  • Right of F = 1 − h, the arc reaches forward past 12: I + 1.
  • The two triangles meet only at h = 0.5, which no double reaches, so they never overlap.
  • The wedge between them is cut into stripes by the nearest tick, round(10F).

Why the extra digit is never 0 or 10. Digit 0 would need F < 0.05. But h ≥ 0.05, so any such dot is already inside the left triangle, and I itself is the answer. Digit 10 would need F ≥ 0.95, which the right triangle already covers. So the 17th digit is always 1–9. Appending it never carries back into I, and it never adds a trailing zero that would have to be stripped.

Try the rain. Random bit patterns land in the wedge about 60% of the time: most doubles really need 17 digits. Math.random() values land there even more often. Decimals that a person typed land in the triangles every time: a decimal with 15 or fewer digits is always found by the short test.

6 · From decision to text

Writing it out

to_decimal hands back I, which may already have been incremented by the carry, together with the digit if there is one. The writer then does three things:

  • turns the 16 digits into characters;
  • drops trailing zeros;
  • puts the decimal point in place, using the exponent of the leading digit, k + 15 + (I ≥ 1015).

Żmij uses fixed notation when that exponent is between −4 and 15, and d.ddde±XX otherwise. So 1e-4 prints as 0.0001 and 1e-5 as 1e-05.

The writer is as branch-free as the decision. It turns the 16 digits into bytes with a few lane-parallel multiplies rather than a divide-by-ten loop, and it counts trailing zeros with one compare and a bit count. Approach B follows that pipeline step by step.

7 · Honesty box

Proved vs tested

ProvedThe regular binary64 path: every double except exact powers of two, subnormals included. The Lean 4 theorem Zmij.correct in test/Zmij.lean (built on test/Core.lean) covers the choice of k, the truncated table, the one multiply, h by shift, the three flags, the +6 and the tie fix. It shows the result, after trailing zeros are removed, is shortest and correctly rounded. It is kernel-checked for all 2,046 exponents.
Caveat: the proof is about a hand-written Lean model of the C++ to_decimal. Nothing checks by machine that the C++, or the generator of its table, matches that model.

TestedThe power-of-two path (the 2,046 lopsided cases; the C++ also sends the smallest normal here). It is not in the Lean proof. verify.py, a Python port, checks all 2,046 directly, and unit tests compare the C++ with Dragonbox for the powers of two below 1.

Testedbinary32: all 232 floats are compared with Dragonbox (float-check.cc).

TestedFormatting: digit generation, trailing zeros, and fixed and scientific layout are covered by unit tests only.

This pageA BigInt port of to_decimal (pinned to v1.2, commit d1682cb) drives every figure. test/explore-zmij-dial.test.js checks it against JavaScript’s shortest output on 200,000 random bit patterns, 50,000 Math.random() values, 50,000 short decimals, all powers of two and 20,000 subnormals. It also checks it against an exact-rational version of the dial on 40,000 more doubles.

8 · Credits

Where it comes from

Each idea on this page has an earlier source:

  • Schubfach (Raffaello Giulietti) showed that one grid step of 10k+1 can hold at most one short candidate, and that the finer grid always has one.
  • yy (Yaoyuan Guo, in yyjson) reduced the work to a single multiply, with the half-ulp taken from the same power-of-ten constant and a truncated table.
  • xjb (Xiang JunBo) scaled by 10−k−1 instead of 10−k, so the integer part is already the short candidate and no division by ten is needed.
  • Żmij (Victor Zverovich, 2025–26) combines these, with branch-free flags, SIMD digit writing and the Lean proofs.

Careful with older write-ups. The December 2025 blog post “Faster double-to-string conversion” describes an earlier Żmij, built from Schubfach plus a trick by Cassio Neri. The code has since been rewritten around the core shown here. This page follows the code at tag v1.2.
