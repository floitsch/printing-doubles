T.1 · The organizing idea

A general algorithm need not be one universal binary

Binary16, binary64, and binary128 have the same kind of interval problem, but they do not have the same exponent range, significand width, cached-power table, or useful machine multiplication.

Tejú Jaguá separates two programs. A C++ generator reads a JSON description of a floating-point type and a target arithmetic strategy. It uses multiprecision integers to derive constants and to reject configurations whose intermediate calculations could overflow. The emitted C source fixes all those choices as macros, tables, and one format-specific function.

The runtime kernel therefore does not parse JSON, call Boost, search for constants, or dynamically choose a limb strategy. Those dependencies belong to the build machine. This distinction is particularly useful when the final target is small or lacks a native integer type twice as wide as its input significand.

T.2 · Generator-to-kernel configurator

Change the format; watch the generated machine change

A carrier is the limb type used by the implementation, not necessarily the storage width of the floating-point format. The checked-in binary16 configurations, for example, use 32-bit limbs. The x86-extended and binary128 configurations use 128-bit limbs and split each stored multiplier limb into two literal fragments because the source language does not provide a convenient portable 128-bit literal.

The multiplier-row count follows the supported decimal-exponent range. It is a useful structural fact, not a complete memory measurement. The displayed source byte count describes the checked-in generated .c file; comments, spelling, compiler padding, dead stripping, and instruction selection prevent it from standing in for linked flash or RAM.

T.3 · The generated algorithm

Try a coarser decimal before computing the fine one

The core accepts a pair m · 2e and returns a decimal pair c · 10f. Decoding signs and special values, and assembling characters such as "1e-3", are deliberately outside this function.

The small-integer route is more than a speed shortcut. If the binary power can be removed by a right shift, conversion becomes exact integer normalization. Trailing factors of ten are detected with modular-inverse arithmetic, so the result can become 1 × 10¹⁰ without entering the cached-power path.

T.4 · Ordinary equal-margin inputs

Map the two boundaries, then ask whether ten times a quotient fits

For an ordinary value, the midpoints to the adjacent floats are equally distant. The source represents their numerators by 2m−1 and 2m+1, adds a small residual shift, and applies one generated cached multiplier. The multiply-and-shift operation turns those boundary numerators into integer images a and b on a decimal scale.

The first candidate is intentionally coarse. The source divides the upper image b by ten to obtain q, then tests s = 10q against the interval from a to b. If s is admitted, q already describes a decimal with one fewer digit and can be returned after removing any further trailing zeros.

If that test fails, the kernel maps the center itself, obtains the adjacent fine-grid integers, and chooses the nearer one. Exact divisibility by powers of five identifies the rare cases where a scaled integer lies exactly on a boundary or halfway between decimal candidates; parity then implements round-to-even. The generated modular-inverse table bounds these tests to the exponents for which a tie is arithmetically possible.

T.5 · Powers of two

The same decision needs unequal boundary constructions

At a normal power of two, the predecessor spacing is half the successor spacing. Tejú Jaguá calls this case uncentered. The upper boundary still derives from 2m+1, while the lower construction uses 4m−1 and an additional division by two. The configurator’s constants have already been checked against the larger intermediates required by this path.

The source again tries the coarser candidate first. Some generated configurations prove that the scaled lower image is always ordered below the upper image; others retain a refined branch for the exceptional ordering. This is why teju_calculation_sorted is generated as a format-specific fact instead of tested through a generic runtime policy.

T.6 · Scope and evidence

A checked-in implementation is not yet a published proof

Traced from generatorJSON parameters; carrier and literal splitting; centered and uncentered overflow checks; 2×limb runtime shift; cached multiplier generation; modular inverses; generated sorted-case fact; emitted C macros and function.

Traced from kernelSmall-integer normalization; centered coarse-candidate test; refined nearest candidate; uncentered power-of-two path; exact power-of-two and power-of-five divisibility; ties-to-even.

Executed nativelyThe checked-in binary64 kernel with native 128-bit support was compiled locally. Decimal pairs were sampled for ordinary, small-integer, power-of-two, long, large-exponent, subnormal, and maximum-finite inputs and fixed as browser-model tests.

Upstream boundaryThe README calls the project partial and work in progress. The core requires finite, strictly positive input and does not emit characters. The promised academic proof is not treated as existing; differential tests against Ryū and Dragonbox remain upstream evidence.

The inspected files, generated-table counts, and native records are retained in the repository’s Tejú Jaguá audit note.
