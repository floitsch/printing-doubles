Chapters / Part II · Scaling and exact intervals

Errol: extend precision, enumerate the residue

Errol represents each scaled quantity with two hardware doubles: a leading approximation and a small offset. This nearly doubles the working precision. Rather than retaining a runtime uncertainty test, Errol3 enumerates the inputs for which the unchecked arithmetic can fail and corrects them with a bit-pattern table.

6.1 · From a checked fast path to a corrected total algorithm

Three versions separate accuracy, verification, and enumeration

Errol’s central experiment is to use native floating-point arithmetic at approximately twice binary64 precision, then account explicitly for the cases where that is still insufficient.

Errol1 constructs a conservative narrow interval with double-double arithmetic. Digit generation inside that interval is correct, but it may miss a shorter decimal in the thin part of the true parsing interval left uncovered by the conservative boundaries. A second, wider computation can determine whether this happened.

Errol2 improves the optimality check. Errol3 then moves the remaining work offline: it removes the conservative narrowing and runtime verification, enumerates every input for which the unchecked core can return a wrong or non-shortest result, and stores corrections for those inputs. At runtime, a bit-pattern lookup precedes the ordinary arithmetic path.

6.2 · High precision from ordinary doubles

Represent x as a leading value plus a non-overlapping offset

A double-double value is a pair ⟨xhi, xlo⟩ denoting their exact mathematical sum. The leading component is the nearest binary64 approximation. The offset records the residual that the leading rounding discarded. The pair must be read as an unevaluated sum: immediately adding the fields with ordinary binary64 arithmetic would round the residual away again.

A decimal analogy is 123.456 represented as 123.5 − 0.044. The first number gives a nearby coarse coordinate; the second says how to move from it. Binary double-double uses the same idea with a vastly smaller offset and with algorithms that reconstruct the rounding error of every operation.

x̃ = x_hi + x_lo, with |x_lo| much smaller than one ulp of x_hiThe residual microscope measures the low component in ulps of the leading double. Its position is significant even when the ordinary-scale marks coincide.

The components are maintained in a non-overlapping form: significant bits present in the leading component do not reappear in the offset. With two 53-bit significands this supplies roughly 106 useful bits, although not every operation is as accurate as one correctly rounded 106-bit hardware operation.

Normalization adds the components once, then reconstructs the rounding residual. If s is the rounded sum, xlo+(xhi−s) recovers the portion lost by that addition under the non-overlap assumptions. The normalized pair is ⟨s, residual⟩.

6.3 · Compensated arithmetic

Recover the error of each operation instead of discarding it

Multiplication splits each double into high and low halves. Four partial products reconstruct the exact product error of the leading components: high×high supplies the rounded product, while the remaining cross terms recover the lower bits. The old offset multiplied by the scalar is added to this product error before normalization.

Multiplication and division by ten receive specialized routines. For multiplication, the code forms the ordinary rounded product and independently evaluates 8x+2x. Their difference exposes the rounding error in 10x. Division performs the inverse reconstruction: multiply the rounded quotient by eight and two, subtract from the original, and place the remaining tenth into the offset.

rounded(10x) − (8x + 2x) reveals the product’s rounding residue.

These formulas matter because digit generation repeatedly subtracts an integer and multiplies the remainder by ten. A small bias in that recurrence would grow until an endpoint crossed a decimal integer and changed the stopping digit.

6.4 · Normalize the parsing interval

Scale both boundaries into the decade [1,10)

Errol estimates the decimal exponent from the binary exponent, looks up a double-double approximation of the corresponding power of ten, and multiplies the input by it. A short correction loop handles an estimate one decade too high or too low. The scaled center lies in [1,10), and the decimal exponent is saved for reconstruction.

The distances to the predecessor and successor supply the lower and upper midpoint offsets. Errol1 divides those distances by a value slightly greater than two to move inward, forming a narrow interval proved to remain inside the exact parsing interval despite later arithmetic error. A companion wide interval uses a slightly smaller divisor and extends outward.

Errol3’s unchecked core removes this deliberate narrowing. It computes midpoint approximations directly, accepting that a finite set of inputs will be mishandled and relying on the generated correction table to intercept them first.

6.5 · Common-prefix generation

Continue while both endpoint pairs have the same integer digit

Imagine that the scaled lower endpoint is 3.31 and the upper endpoint is 3.38. Both lie in decimal cell 3, so every point between them begins with the digit 3. After recording that digit, subtract 3 and multiply by ten. The new interval is [3.1, 3.8], which exposes the next digit. Repeating this crop-and-enlarge operation extracts the complete common prefix.

On every iteration, Errol performs that construction with double-double endpoints. If a leading component is itself an integer but its offset is negative, decrement the truncation: the represented pair is just below that integer. When the two digits agree, append the digit, subtract it from both pairs, and multiply both remainders by ten with compensated arithmetic.

When the endpoint digits differ, the common prefix is complete. The core rounds the position midway between the two remaining endpoints to obtain the final digit, breaking an exact decimal tie toward an even digit.

  1. represent each scaled endpoint as a normalized (hi, lo) pair
  2. estimate and correct the decimal scale so the leading digit is exposed
  3. append common endpoint digits; update both remainders with compensated ×10
  4. before the unchecked core, return a generated correction for exceptional input bits

This is close to the common-prefix view of Dragon, but the representation and proof obligation differ. Dragon’s integer margins are exact. Errol’s endpoints are very accurate floating-point pairs whose residual failure set is established offline.

6.6 · Correctness is not yet optimality

A narrow interval may omit a shorter valid decimal

If a generated decimal lies in a conservative interval wholly contained within the parsing interval, it certainly recovers the input. That does not establish shortestness with respect to the complete parsing interval. A shorter decimal may lie in one of the uncovered strips between a narrow boundary and the exact midpoint.

Errol1 therefore also computes with a widened interval. A shortest result from the wide interval need not itself be valid, but its length is a lower bound on what the exact interval could contain. When the narrow and wide computations produce equal lengths, the narrow result is certified optimal. Errol2 analyzes possible decimal midpoints in the uncovered strips more directly and reduces the cases requiring uncertainty.

6.7 · Errol3’s offline proof step

Search exceptional decimal midpoints, not all 264 bit patterns

Brute-force enumeration of every binary64 input would be an unattractive proof technique. The paper instead characterizes potentially pathological outputs through decimal midpoints. A shortest binary64 rendering has at most seventeen significant digits; only shorter decimal midpoints capable of approaching a parsing boundary need be examined.

The enumeration constructs structured sequences of shifts between midpoint congruence classes. It advances to the first offset that moves a midpoint closer to zero, alternately approaching from above and below. Once a midpoint enters the derived error neighborhood, nearby shifts are searched exhaustively. Subnormal ranges are covered by changing the effective precision associated with the exponent.

The resulting input bit patterns are stored in a search-friendly level-order table together with corrected digit strings and exponents. The runtime function performs the table lookup first. Only a miss enters the unchecked double-double core.

6.8 · Executable common-prefix geometry

Each shared digit becomes the next complete line

The ten boxes are not a program counter. They are the current decimal partition of the scaled interval. At each depth, the endpoint markers either select one common box or demonstrate that no further digit is shared.

For 1/3, move the depth control from left to right. The endpoints repeatedly remain in cell 3. Their separation grows tenfold at every level because the selected cell is stretched to the full line. At the sixteenth level they finally occupy cells 2 and 3; that separation determines the final rounded digit.

The 0.3 example demonstrates why the residual matters at an integer. The lower endpoint is represented just below 3 and therefore truncates to 2, while the upper endpoint is just above 3 and truncates to 3. They have no common leading digit in the normalized interval, so the middle is rounded immediately to 3 and the saved exponent restores 0.3.

The checked-correction preset is deliberately about this browser model, not a claimed member of Errol3’s native table. Its idealized pair core produces 34562081242061270; the independent exact control returns 34562081242061268. The teaching wrapper detects and replaces the disagreement at runtime. The native algorithm’s different mechanism is described next.

6.9 · Primary-source discrepancies

The corrected artifact must accompany the paper

The corrected paper reports 45 exceptional inputs for Errol3. The current public repository at commit 5364de45fcecd91a3795c93e4f8cc680d34ccabf declares errol_enum3[432] and an equally sized correction array. The repository does not explain this ninefold difference in its short history. This chapter therefore records both figures and treats 432 as the fact about the pinned current artifact, without claiming that it is the same set described in the paper.

The repository also carries a performance correction. The original evaluation accidentally compared Errol with a Grisu3 build lacking optimization and reported an advantage. Corrected measurements showed Errol approximately twice as slow as optimized Grisu3 on that setup. The updated paper reports Errol3 as 2.4× slower than Grisu3 and than Grisu3 with Dragon4 fallback on its measured distribution. These historical measurements should not be generalized to current processors or microcontrollers.

The authoritative materials used here are the corrected paper and the public implementation and correction notice.

6.10 · Evidence and implementation status

The arithmetic core is executable; the native table remains distinct

Implemented in the browserRational-to-double-double decomposition; normalization; split-product compensation; specialized multiplication and division by ten; exact midpoint scaling for the teaching input; endpoint truncation; common-prefix digit generation; decimal tie-to-even; checked correction path.

Deliberate idealizationThe browser constructs each starting pair directly from the exact rational boundary. It does not copy the native power table or claim bit-for-bit equivalence with errol3u_dtoa. The checked wrapper uses the independent exact oracle where the idealized core disagrees.

Corpus evidenceFamiliar values and hard transitions pass the pair core; the checked wrapper agrees with the exact oracle for 10,000 deterministic bit patterns and is required to exercise a disagreement.

Native artifact evidenceThe pinned public source uses 432 bit-pattern corrections despite the corrected paper’s statement of 45. A compiled differential harness and provenance audit of that expansion remain necessary before calling the browser code a faithful Errol3 port.
