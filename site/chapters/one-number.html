The task

Print fewer digits. Read back the same value.

When a computer reads a decimal, it rounds to the nearest value its binary format can store. Several different decimals can therefore round to the same stored value.

A printer uses this freedom. It looks for the decimal with the fewest significant digits that rounds back to the original value. If several are equally short, we want the closest one.

To keep the numbers small, we’ll use a miniature format with 8 significant binary bits. Our stored value is exactly 6.28125, or 201/32. The neighboring stored values are 6.25 and 6.3125.

The midpoints between these values mark the limits of rounding back to 6.28125. We call the range between them its rounding interval:

6.265625 < decimal < 6.296875. The shortest choices are 6.27, 6.28, and 6.29; 6.28 is closest.

6.28 works even though it is not exactly 6.28125. Reading 6.28 in our miniature format rounds it back to 6.28125. The same is true of 6.27 and 6.29.

Can we use fewer digits? The nearest two-digit choices, 6.2 and 6.3, both lie outside the interval. So we need three significant digits. Of the three-digit choices inside, 6.28 is closest.

The answer is settled. Now we can ask how each algorithm finds it without first calculating the entire decimal expansion.

What happens exactly at a boundary?

At a midpoint, two stored values are equally close. The usual rule chooses the one whose binary significand is even. Our value is 201/32, with the odd significand 201, so both boundary points round to its neighbors. That is why this example excludes the endpoints.

What changes for a real double?

Binary64 has 53 significant bits rather than 8. Its rounding intervals are much narrower, and the calculations need larger integers. The task is the same.

6.28 is the answer for our miniature format only. For binary64, the shortest text for this value is 6.28125. The full algorithm chapters use binary64 inputs.

Dragon · Build from the left

Long division, with permission to stop early

Dragon produces digits by long division, starting at the left. After each digit it tests two choices: stop with the digits written so far, or round the last digit up.

With just 6, the choices are 6 and 7. Neither is inside the rounding interval. With 6.2, the choices are 6.2 and 6.3. Still neither. Reveal the next digit below to see when stopping becomes possible.

6 or 7: neither fits. 6.2 or 6.3: neither fits. 6.28 or 6.29: both fit; choose 6.28.

Long division tells us the digits already written—the prefix—and how much remains. Dragon also tracks the distance from the stored value to each boundary. These distances are the allowed errors.

Once a choice is inside the interval, Dragon can stop. It does not need to finish the exact expansion. Here, 6.28 and 6.29 both fit, and 6.28 is closer.

Connect the picture to Dragon’s R, S, and margins

Use a common denominator of 64. The value is 402/64; the boundaries are 401/64 and 403/64. So the initial numerator R is 402, denominator S is 64, and both allowed margins are 1.

First: 402 = 6 × 64 + 18. Next: 180 = 2 × 64 + 52. Next: 520 = 8 × 64 + 8. At each new digit, multiply both the remainder and margins by ten. The margins become 1, 10, then 100. At the third digit, the distance down is 8 and the distance up is 64 − 8 = 56. Both are below 100; 8 is smaller, so keep 6.28.

Ryū · Shorten from the right

Cross out a decimal place. Does any answer survive?

Ryū starts with enough decimal places and then removes the ones it does not need. With three places after the point, the decimals inside our interval run from 6.266 through 6.296, in steps of 0.001.

Write these as integers, with the decimal point’s position kept separately: 6266 through 6296, each divided by 1000. Only the two ends need to be stored.

Which of these decimals can be written with one fewer place? The ones ending in zero: 6.270, 6.280, and 6.290. In integer form, keep 6270, 6280, and 6290, then divide by ten. We get 627, 628, and 629, now each divided by 100.

Thousandths: 6266…6296. Hundredths: 627…629. Tenths: empty. Choose 628 × 0.01 = 6.28.

Try removing another place. None of 627, 628, or 629 ends in zero, so no answer survives at tenths. Stop at hundredths and choose 628, meaning 6.28.

Ryū shortens the set of possible answers. It keeps track of the interval while removing digits; simply truncating one guessed string would not do that.

Where does the initial integer interval come from?

In this small example, multiply the boundaries by 1000: 6265.625 and 6296.875. The integers strictly between them are 6266 through 6296. In Ryū, the input’s binary exponent determines a sufficiently fine starting decimal scale. Cached powers of five and binary shifts produce the necessary integer information with bounded machine arithmetic. The production loop keeps endpoint and discarded-digit flags; our picture shows their exact set meaning.

Do a power-of-five multiply and a binary shift by hand

For our value, thousandths require the integer part of 201 × 1000 / 32. Factor 1000 into 8 × 125 and cancel the 8 against 32. What remains is 201 × 125 / 4. The 125 is a power of five: 5³.

No floating-point multiplication was needed. For real doubles the powers are larger, and some scales need reciprocals. The hard part of Ryū’s proof is showing how many multiplier bits suffice, and which remainder facts must be preserved.

Schubfach · Use the width

Use the interval’s width to choose two spacings

Ryū repeatedly removes decimal places. Schubfach can work out which two spacings to try from the interval’s width.

Picture decimals as the teeth of a comb. At hundredths, the teeth are 0.01 apart. Our interval is 0.03125 wide, so it is too wide to fit between two teeth: at least one hundredth must lie inside.

At tenths, the teeth are 0.1 apart. The interval is narrower than that gap, so it can contain at most one tenth.

Try tenths first. If none fits, use hundredths. Move the interval below. Its width stays the same, but it sometimes contains a tenth and sometimes does not.

The interval is wider than 0.01 and narrower than 0.1. No tenth fits the interval around 6.28125; the nearest hundredth, 6.28, does.

For 6.28125, tenths miss. At hundredths, we only need to compare 6.28 and 6.29, the two decimals immediately below and above the stored value. Although 6.27 is also inside, it is farther away than 6.28. It cannot win.

Why can’t an even shorter decimal escape this argument?

Every whole-number tooth also belongs to the tenths comb, and every tenths tooth belongs to the hundredths comb. These sets are nested. If the tenths comb misses, all coarser combs miss too. If a tenth fits and has trailing zeros in its significand, remove those zeros without moving the tooth. For general inputs, the interval width chooses the pair of decimal spacings; the proof also handles endpoint inclusion and the unequal spacing at powers of two.

Dragonbox · Measure from the right

The division remainder is a distance

Dragonbox builds on Schubfach’s choice of spacings. To test tenths, start at the interval’s right edge and measure back to the first tenth on its left. If that distance is less than the interval’s width, the tenth is inside.

Here, the right edge is 6.296875. The first tenth to its left is 6.2, a distance of 0.096875. That is greater than the interval’s width, 0.03125, so 6.2 is outside. The next tenth, 6.3, is past the right edge. Tenths fail.

Right edge 6.296875 = 62 × 0.1 + 0.096875. The remainder, 0.096875, is greater than the interval width, 0.03125. Tenths fail; try hundredths.

Division gives us both facts at once. There are 62 complete tenths before the right edge, with 0.096875 left over. The quotient, 62, gives the candidate 6.2. The remainder, 0.096875, is the distance back to it.

If tenths fail, Dragonbox reuses this remainder to find the next digit. It does not need to start the scaling calculation again.

How does the remainder give the next digit?

Our interval is symmetric, so the stored value is half the width left of its right edge. Subtract that half-width from the remainder: 0.096875 − 0.015625 = 0.08125. This is the distance from 6.2 to the stored value.

The nearest hundredth to that distance is 0.08. Add it to 6.2 to get 6.28.

In the binary64 implementation, a larger scale turns these into tests using divisors 1000 and 100. For this example, multiplying by 10000 would give 62968.75 = 62 × 1000 + 968.75, with width 312.5. The comparison is unchanged.

Grisu · Make uncertainty visible

A blurred boundary can still settle a decision

So far, our comparisons have been exact. Grisu uses faster, approximate scaling. It keeps a bound on the error, so it knows that each true boundary lies somewhere within a narrow band.

A decimal is definitely inside only if it stays inside for every boundary position allowed by those bands. Increase the uncertainty below to see when that proof stops working.

If the possible lower boundary is 6.264625…6.266625, 6.28 is definitely above it. If the uncertainty grows to 6.245625…6.285625, membership of 6.28 is unresolved.

With narrow bands, 6.28 is clearly inside. With wider bands, a boundary might lie past it. The decimal has not moved. We no longer know enough to prove that it is inside.

Grisu3 returns an answer only when its checks prove that it rounds back, is shortest, and is the closest such choice. Otherwise, it hands the input to an exact algorithm such as Dragon.

Errol · Save what rounding throws away

Keep a main measurement and a correction

Imagine a measuring device that reports only three significant decimal digits. It reports our value as 6.28. The part it lost is +0.00125. Write both down. Together, they still describe 6.28125.

6.28 + 0.00125 = 6.28125. Relative to the threshold 6.28, the main word says “on it”; the saved correction says “above it.”

Suppose we need to know whether the value is above 6.28. The main measurement alone looks equal to 6.28. The positive correction tells us it is above.

Errol uses the same idea with two binary doubles. It keeps them separate, as a main value plus a small correction. This is called double-double arithmetic. Rounding their sum back to one double would lose the extra precision.

Errol carries paired values through scaling and digit generation. More precision reduces ambiguous cases; it does not by itself prove there are none. Errol3 also uses a precomputed correction table for its exceptional inputs.

Coonen · A different question

What if the caller supplies the number of digits?

The earlier algorithms find how many digits are needed. Coonen starts with a request such as “give me four significant digits.”

For 6.28125, move the decimal point three places right: 6281.25. Round to the integer 6281, then move the point back: 6.281. The requested length takes the place of a shortest-answer search.

Four digits: 6.28125 × 1000 → 6281.25 → round to 6281 → divide by 1000 → 6.281.

The difficulty is carrying out the scaling accurately with a limited number of binary bits. Coonen’s algorithm controls the extra error introduced by this calculation.

Now the machinery has a purpose

Two different problems were hiding in the code

First, decide which decimal to choose. That is what the intervals, combs, and distances explain. Then compute those decisions quickly and reliably, using the arithmetic the machine provides.

Often a calculation only needs to answer “below, equal, or above?” It does not need every digit of the exact result. Powers stored in tables, wide integer products, and flags for discarded bits help obtain that answer. Their proofs show why the information kept is enough.
