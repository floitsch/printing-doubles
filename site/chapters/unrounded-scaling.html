Unrounded scaling: keep the decision, discard the digits

A single primitive rescales a binary integer by powers of two and ten, but postpones rounding. It returns the integer bits, the half bit, and one sticky bit—enough information for fixed-width printing, shortest printing, and parsing.

U.1 · The representation

Do not answer a rounding question before it has been asked

Scaling ultimately produces an integer, but different callers need floor, ceiling, nearest, or an endpoint adjusted by one unit. Returning an already rounded integer would force the scaling primitive to guess which policy comes next.

An unrounded number retains the integer part and two additional bits. The first is the binary half bit: it says whether the fractional part is at least 1/2. The second is sticky: it is one when anything after the half bit is nonzero. Many discarded bits are compressed to one fact, but it is precisely the fact that separates an exact integer or exact half from a value just beyond it.

The notation 6.5+ does not mean a particular decimal such as 6.51. It represents every value strictly between 6.5 and 7. From those three fields, integer rounding toward either direction and round-to-nearest-even are still determined exactly.

U.2 · The common operation

Scale by binary and decimal powers, but return the unrounded form

The primitive computes the unrounded form of x · 2e · 10p, where x is an unsigned integer. A slow specification can form an exact rational with big integers, retain two fractional bits, and OR every remaining bit into sticky. The fast implementation must return the same bit pattern using fixed-width products.

Each power 10p is represented by a normalized 128-bit integer rounded upward and a binary exponent. Rounding the table entry upward is intentional: it lets the optimized implementation represent the cached power as pm.hi · 2⁶⁴ − pm.lo. The first multiplication therefore gives a ceiling estimate that requires correction only when a borrow could cross the retained-bit boundary.

U.3 · Executable product and proof microscope

See which words are retained, summarized, corrected, or never computed

The browser reconstructs the pinned 696-entry power table from exact rational powers of ten, executes the optimized subtract-form algorithm with BigInt, and independently evaluates the mathematical unrounded result. The comparison is therefore bit-for-bit; it is not an oracle-chosen decimal laid over a merely suggestive product diagram.

The first 64×64 multiplication produces the approximate top and middle words. When any of the top word’s discarded s bits is one, a borrow from below must stop before it reaches the retained region. Sticky is already known to be one, so the correction multiplication can be omitted. If those bits are all zero, the high half of x · pm.lo determines the borrow and sticky state. The low half remains unnecessary in both cases.

U.4 · Why 128 cached bits are enough

The error is small; the proof shows it cannot hide at a decision boundary

The cached power is the ceiling of an exact normalized power of ten, so its error is less than one unit in its 128-bit scale. Multiplying by x enlarges that error, but x is left-justified and at most 64 bits. The implementation discards the lowest 64 product bits entirely: these are exactly the bits whose individual values cannot be trusted.

That argument still leaves a danger. An error in the discarded region might carry or borrow into the retained result, or it might make a genuinely nonzero tail appear zero. The proof separates three regimes:

Small positive pThe relevant power of five is exact in the upper cached word. The omitted low region contains only zeros, so no information is lost.

Small negative pExact divisibility identifies integer results. Otherwise the repeating binary fraction stays farther from an integer threshold than the maximum table error and necessarily sets sticky.

Larger |p|An Ivy-backed finite-domain argument proves that the middle region cannot take the dangerous value that would let approximation error pass unnoticed.

The companion proof states the parameter ranges explicitly: for p between −400 and 400, it covers the bit widths and retained precision used by both printing and parsing. This is stronger evidence than a difficult-case corpus, although the executable port and native tests remain useful checks against transcription mistakes.

U.5 · Build shortest conversion on the primitive

Scale the interval, then make the decimal choice with ordinary integer operations

The shortest printer left-justifies the binary64 significand and constructs integer numerators for the lower and upper parsing boundaries. Each boundary is passed through unrounded scaling at one selected decimal exponent. A one-unit nudge encodes whether an exact endpoint is included, after which ceiling and floor produce the first and last admissible decimal integers.

Following the key Schubfach observation, the algorithm first divides the upper admissible integer by ten and asks whether appending a zero would remain above the lower limit. If so, a coarser decimal exists and is immediately shortest. Otherwise the fine grid contains either one candidate or several adjacent candidates. In the latter case only, the center value is scaled and rounded to choose the closest.

This source structure is implemented in the browser, not just the primitive. The tests compare its normalized coefficient and exponent with the independent exact interval oracle over difficult fixed cases and a deterministic bit-pattern corpus. The same primitive also supports fixed-width output—select a decimal scale, call it once, and round—and decimal parsing, where the input digit integer is scaled in the opposite direction before it is packed as binary64.

A unified primitive does not make tables or formatting disappear

Storage factThe pinned table covers −348 through 347: 696 pairs of 64-bit words, or 11,136 bytes of raw table payload before code and object-format effects. This is not a complete flash or RAM measurement.

Performance boundaryThe published benchmark results are measurements on named Apple and AMD systems. The site does not turn them into a universal ranking or an ESP32 prediction.
