The current frontier: arithmetic is no longer the whole formatter

Recent implementations retain the interval geometry developed by Ryū and Schubfach, but reduce wide products, branches, divisions, table traffic, and digit-writing costs. Their evidence is uneven and changes quickly. This chapter pins sources and separates algorithms with published proofs from work-in-progress implementations and benchmark claims.

10.1 · Evidence is part of the algorithm

Correct output, fast arithmetic, and fast formatting are different claims

At a few nanoseconds per conversion, benchmark conclusions are properties of a complete experiment: processor, compiler, flags, input distribution, cache state, API, and formatting rules.

The fixed-width chapters established a mathematical core: select the shortest closest decimal pair that lies in the parsing interval. A library must additionally decode special values, write digits, choose fixed or scientific notation, preserve or suppress a negative zero, and respect an API contract. Current work often gains as much from these surrounding steps as from candidate selection.

This chapter uses four evidence labels:

ProofA mathematical development or machine-checked argument connects bounded operations to an exact specification.

Differential testsThe implementation is compared with an independent converter over exhaustive smaller formats, structured hard cases, or large generated corpora.

Implementation claimA repository documents a contract and contains tests, but the complete proof may be forthcoming or distributed through code comments and generators.

Benchmark claimA measured result for named hardware and software. It is evidence for that configuration, not a timeless ordering.

10.2 · Żmij

Fuse the Schubfach selection with digit production

Żmij is a compact C and C++ formatter derived from Schubfach and influenced by yy, Dragonbox, and xjb. Its repository describes one multiplication by a cached decimal power in place of three, faster integer logarithm approximations, specialized division and remainder, fewer conditional branches, compact storage of powers, and scalar or SIMD digit emission.

The double path adopts xjb’s 10−k−1 scaling, exposing the final decimal digit without an additional division on the critical path. The output stage uses binary-coded-decimal techniques and architecture-specific SIMD where available. This is an important change of emphasis: once candidate selection is tight, turning a 17-digit integer into bytes can dominate.

The repository claims shortest, correctly rounded round trips for binary32 and binary64 and carries boundary and differential tests. Its benchmark charts name the processor, operating system, compiler, and comparison suite. The magnitude of the reported advantage differs substantially between Apple M5 and AMD EPYC systems, which is itself useful evidence that there is no architecture-independent “fastest” ordering.

10.3 · Tejú Jaguá

Generate a conversion kernel from the floating-point format

Tejú Jaguá separates the core selection from decoding and string assembly. Its C header accepts generated parameters describing a floating-point type and target integer capabilities. A C++ generator produces format-specific constants and wrappers. Checked-in configurations include binary16, bfloat16, binary32, binary64, x86 extended precision, and binary128, with variants for targets that do or do not provide a native 128-bit integer.

This parameterization is unusually relevant to embedded systems: it makes word-width assumptions and constant generation explicit. It also prevents an accidental equation of “works for double on x86-64” with “is a general format algorithm.”

The upstream README calls the work partial and work in progress. The core handles only finite, strictly positive inputs and returns a decimal pair; sign, zero, infinities, NaNs, and final string production are outside that function. It states that an academic proof paper will be written. The test build compares results with Dragonbox and Ryū and uses Boost multiprecision in its generator and test infrastructure, not in the runtime kernel.

10.4 · xjb

Compute the last digit directly from one scaled fraction

xjb presents a Schubfach-derived selection in which k is chosen from the binary spacing, then the value is scaled by 10−k−1. The integer part supplies all but the last decimal digit. The fractional part is multiplied by ten and rounded to obtain the last digit; interval-width tests may replace it with 0 or 10 to obtain a shorter admissible neighbor.

This formulation makes the decisive alternatives visible in one coordinate system. Ordinary spacing uses symmetric half-width tests. An irregular power-of-two interval uses separate lower and upper distances. Endpoint equality consults the stored binary significand parity.

The repository provides scalar and SIMD float-to-string implementations, JSON-specific formatting, full and compressed tables, and comparison tests. It reports full/compact table data of 1,352/64 bytes for binary32 and 15,336/368 bytes for binary64. These are upstream source figures, not independently reproduced linked-image measurements.

The April 2026 preprint is explicitly not peer reviewed, and the repository says Algorithm 1 in the article contains a mistake and that the README and implementation should be followed instead. Big-endian support remains on the roadmap. These qualifications are material when assigning confidence.

10.5 · Fast unrounded scaling

Return retained bits plus a sticky bit, not a rounded product

Russ Cox’s unrounded-scaling work builds a shared primitive for fixed-width printing, shortest printing, and decimal parsing. An unrounded value retains the high result bits and one sticky bit saying whether any discarded bit was nonzero. This is the software analogue of information carried between stages of an IEEE 754 arithmetic pipeline.

To scale x·2e by 10p, the implementation uses a 128-bit cached multiplier and conceptually forms a 192-bit product. It need not calculate the lowest word. Two 64×64→128 multiplications provide the upper and middle words; the middle word and the low shifted bits of the high word determine the sticky bit.

The subtle point is proving that rounding the cached power upward cannot carry into the retained result unnoticed. For small powers, exact divisibility or separation from integer thresholds is sufficient. For large powers, an Ivy proof analyzes the table entries and shows that the relevant middle region cannot be the dangerous all-zero pattern. A companion proof document makes these finite-domain checks executable.

Shortest formatting then resembles an exact Grisu2: scale the center and interval information into a small unrounded type, produce a candidate, and trim zeros while retaining exactness information. There is no Grisu3 rejection because the scaling result itself is proved exact in the unrounded representation.

10.7 · Microcontroller research track

Source table size is not linked firmware size

Compact-cache modes can change read-only data by an order of magnitude, but a useful ESP32 comparison also needs generated instructions, helper routines for wide multiplication and division, relocation data, alignment, exception support, and which character-formatting paths the linker retains. SIMD code is irrelevant on many microcontrollers; a native 128-bit C type may expand into sizable compiler helpers.

The independent measurement suite will therefore compile identical APIs for the same target, compiler, flags, notation contract, and link-time optimization setting. It will report text, read-only data, writable data, stack high-water mark, and whether wide-arithmetic helpers were linked. Until those measurements exist, this site repeats only explicitly attributed upstream table figures and makes no recommendation for ESP32.
